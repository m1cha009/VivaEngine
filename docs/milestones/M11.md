# M11: Model loading

## What was built

The engine loads 3D models from **glTF** files, the format most 3D tools export, and turns them
into GameObjects.

- **`Viva/Model.h`**:
  - `Model::Load(renderer, "models/CesiumMilkTruck.glb")` reads a `.gltf` or `.glb` file, uploads
    its meshes and textures to the GPU, and creates its materials.
  - `model->Instantiate(scene, parent)` creates the model's GameObjects: one named after the file,
    with the file's hierarchy of nodes below it. Call it as often as you like: every instance
    shares the same GPU resources.
- **`MeshRenderer`** draws a list of **parts**, each a mesh with its own material, instead of one
  pair. A glTF mesh can be several pieces with different materials. `AddComponent<MeshRenderer>(mesh,
  material)` still works for the single case.
- **`Transform::Find("Body/Wheels")`** finds a child by name, like Unity's `transform.Find`.
- **`Renderer::CreateTexture(width, height, pixels)`** makes a texture from pixels in memory.
- **New dependency:** [cgltf](https://github.com/jkuhlmann/cgltf) 1.15, a glTF parser in a single C
  header (MIT license). It was approved for this milestone.
- **Two models** from the Khronos Group's glTF Sample Assets, both CC BY 4.0. The credits, with a
  notice about the Cesium logo both show, are in
  [`assets/models/CREDITS.md`](../../assets/models/CREDITS.md):
  - `BoxTextured`, a 1 m cube with the Cesium logo: a `.gltf` with a `.bin` and a `.png` next to
    it.
  - `CesiumMilkTruck`, a truck made of 2 meshes, 4 materials and one texture: a single `.glb`.
- **Sandbox:** a logo box sits on each pillar (eight instances of one model), and the milk truck
  drives around everything with its wheels turning.

## Concepts

### glTF

glTF ("GL Transmission Format") is the Khronos Group's file format for 3D scenes and models. It's
sometimes called "the JPEG of 3D": a compact format meant for loading, not for editing. Blender
exports it, and so do most other tools. It comes in two flavors:

- **`.gltf`**: a JSON text file that describes the model, plus separate files for the binary data
  (`.bin`) and the images (`.png`, `.jpg`). Open `assets/models/BoxTextured/BoxTextured.gltf` in a
  text editor and you can read the whole model.
- **`.glb`**: the same JSON and the same binary data packed into one binary file. Images live
  inside it too.

The JSON is a set of arrays (`nodes`, `meshes`, `accessors`...) whose entries refer to each other
by index:

```
scene ──→ nodes       a hierarchy: a name, a position/rotation/scale, maybe a mesh, children
            └─→ mesh ──→ primitives   one per material
                          ├─ attributes   POSITION, NORMAL, TEXCOORD_0, COLOR_0... ─→ accessors
                          ├─ indices      ─→ accessor
                          └─ material ──→ base color factor, base color texture ─→ image
accessor ──→ buffer view ──→ buffer       the .bin file, or the binary part of a .glb
```

An **accessor** says how to read one array out of the binary data: how many elements, what each
one is (`"type": "VEC3"` with `"componentType": 5126`, the OpenGL code for float, is three floats),
and which **buffer view** (a byte range of a **buffer**) holds them. In `BoxTextured.gltf`,
accessor 2 is the 24 vertex positions, and its `min`/`max` show the cube spans -0.5 to 0.5.

glTF's conventions are the engine's, which is no accident (M6 and M10 chose them): right-handed, +Y
up, a model's front faces +Z, front faces are counter-clockwise, units are meters, and texture
coordinates start at the image's top-left corner. So nothing gets flipped or converted while
loading. Unity's importer has to convert everything into its left-handed space.

### Load and Instantiate: a model is a prefab

In Unity, importing a model creates an asset, really a prefab, with its meshes, materials and
textures. Dragging it into the scene, or calling `Instantiate`, creates GameObjects from it. M11
works the same way:

| Unity | VivaEngine |
|---|---|
| Importing `truck.glb` into Assets | `Model::Load(renderer, "models/CesiumMilkTruck.glb")` |
| `Instantiate(truckPrefab, parent)` | `truck->Instantiate(scene, &parent)` |
| `transform.Find("Body/Wheels")` | `GetTransform().Find("Body/Wheels")` |
| A mesh's submeshes and `MeshRenderer.sharedMaterials` | `MeshRenderer::Parts`: a mesh and a material per part |
| `new Texture2D(w, h)`, `SetPixels32`, `Apply()` | `renderer.CreateTexture(w, h, pixels)` |

`Load` does the expensive work once: it reads the file, decodes the images and uploads everything
to the GPU. `Instantiate` only creates GameObjects and components, whose `MeshRenderer`s point at
the model's meshes and materials through `shared_ptr`s. That's why eight logo boxes cost eight draw
calls but no extra memory, and why destroying one of them frees nothing: the other seven still use
the mesh and the texture.

The `Model` itself can go once its instances exist; they keep what they use alive. `LoadDemoScene`
holds its models in local `unique_ptr`s, which are destroyed at the end of the function. A game
that wants to spawn more instances later (M12's obstacles) keeps the `Model` as a member instead.

### Nodes become GameObjects

Every node in the file becomes a GameObject with the node's name and local position, rotation and
scale, and nodes with a mesh get a `MeshRenderer`. The truck's hierarchy, as the Scene window shows
it:

```
CesiumMilkTruck            the instance's top object, named after the file: the game places this one
└── Yup2Zup                turns the truck upright (it was built in a tool where Z points up)
    └── Cesium_Milk_Truck  the body: 3 parts (white paint, glass, window trim)
        ├── Node           where the front axle is
        │   └── Wheels     the front wheels: one mesh with both sides
        └── Node.001       where the rear axle is
            └── Wheels.001 the rear wheels: the same mesh again
```

A node's place comes in one of two forms. Usually it's a translation, a rotation quaternion and a
scale, which map directly onto the Transform (glTF writes a quaternion as x, y, z, w; GLM's
`quat::wxyz` takes w first). Sometimes it's one 4×4 matrix, like the top node of `BoxTextured`.
The loader takes such a matrix apart:

- column 3 is the position;
- the first three columns are the node's own axes, each as long as the scale along it, so their
  lengths are the scale;
- divided by those lengths, the columns form a pure rotation matrix, which `glm::quat_cast` turns
  into a quaternion.

The file's main scene lists the nodes at the top of the hierarchy, and `Instantiate` builds each of
those with **recursion**: `InstantiateNode` creates one GameObject, then calls itself for each child,
which does the same for its own children, until the leaves.

### Meshes made of parts

A glTF mesh is a list of **primitives**, each with its own vertices and its own material. The truck
body has three: the white paint (textured), the glass and the window trim. Unity would import that
as one Mesh with three submeshes, and the MeshRenderer would get three materials. Here each
primitive becomes its own `Mesh`, and the MeshRenderer gets a list of parts, each pairing a mesh
with its material. The renderer didn't need to change: every part is one `Submit`, so one draw
call. The truck takes five (three for the body, one per axle).

From each primitive the loader reads the positions, the first set of texture coordinates, the
vertex colors if there are any (white otherwise), and the indices. Normals and the rest are left
for when there's lighting.

### Materials and textures

glTF materials are **PBR** ("physically based rendering"): a base color plus metalness, roughness,
a normal map, ambient occlusion and emission, which together describe how light interacts with the
surface. The renderer has no lighting yet (that's beyond M12), so only the base color is used: a
color times a texture, exactly what the Unlit shader does. glTF colors are linear, like the
engine's material colors.

The images come in two ways:

- **Next to a `.gltf`**, referred to by a URI ("CesiumLogoFlat.png"). The loader hands those to
  `Renderer::LoadTexture`, so they share the texture cache from M8.
- **Inside a `.glb`**, as the bytes of a PNG or JPEG in the binary data. The loader decodes them
  from memory with stb_image (`DecodeImage`, split out of M7's `LoadImageFile` for this), then
  creates the texture with `CreateTexture(width, height, pixels)`.

`LoadTexture` now works the same way inside the renderer: `LoadImageFile`, then `CreateTexture`.
Every texture comes through `CreateTexture`, which checks that the pixels match the size, and the
Vulkan `Texture` class only turns pixels into a GPU image.

The truck's wheels and body use one 2048×2048 JPEG between them, through two different texture
entries. The loader keeps one texture per image, so it's decoded and uploaded once: about 21 MB of
GPU memory with its mipmaps (2048 × 2048 × 4 bytes, plus a third for the smaller levels).

### Using a C library from C++

cgltf is written in C, which has no classes, destructors or exceptions. Three things in `Model.cpp`
bridge that:

- **A `unique_ptr` with a custom deleter.** `cgltf_parse_file` hands back a `cgltf_data*` that must
  be freed with `cgltf_free`. `std::unique_ptr<cgltf_data, CgltfDeleter>` calls it automatically when
  it goes out of scope, on every return path. That's RAII for C resources, the job C#'s `using`
  block does.
- **Callbacks.** cgltf reads files through function pointers you can replace (C#'s delegates). The
  loader passes `ReadFile`, which reads through the engine's `ReadBinaryFile`: UTF-8 paths on every
  OS, like shaders and textures. C can't take a `std::vector`, so the bytes are copied into memory
  from `std::malloc`, which `ReleaseFile` later frees with `std::free`.
- **Result codes.** Each cgltf call returns a `cgltf_result`, checked after each step. Before
  trusting anything, `cgltf_validate` checks that every offset and index stays inside the data. A
  broken file then gets a clear error message instead of a crash.

### Finding children by name

`Transform::Find("Node/Wheels")` works like Unity's: it looks among the direct children for one
with the first name, and a `/` continues from there, one level per name. The sandbox finds both
axles with whole paths, such as `"Yup2Zup/Cesium_Milk_Truck/Node/Wheels"`, and adds a `Spinner` to
each. glTF doesn't require names to be unique, so if the rest of a path isn't below the first
child with a name, `Find` tries the next child with that name.

The path is a `std::string_view`: a view of characters stored somewhere else, like C#'s
`ReadOnlySpan<char>`. Cutting it into pieces with `substr` copies nothing.

### Rolling wheels

The file animates the wheels, but the engine doesn't play animations yet, so a `Spinner` turns
them. For a wheel to roll rather than slide, each turn must cover its circumference, 2π × radius.
So its speed in radians per second is the truck's speed divided by the wheel's radius:
3 m/s ÷ 0.43 m ≈ 7 rad/s, or 400°/s, which the inspector shows. The same formula turns the truck's
pivot: 3 m/s on a circle of 9.5 m is 0.32 rad/s, about 18°/s.

The direction comes from the right-hand rule. The axle is the file's Y axis, and rolling forward
means turning the negative way around it. To check, point your right thumb along an axis: your
fingers curl the positive way around it.

## Reading guide

1. **`sandbox/src/DemoScene.cpp`**: `Model::Load`, `Instantiate` (the boxes on the pillars), the
   truck on its pivot, and `Find` with the wheel spinners.
2. **`engine/include/Viva/Model.h`**: the public API, and the private `Node` that remembers the
   file's hierarchy.
3. **`assets/models/BoxTextured/BoxTextured.gltf`**, in a text editor, next to the glTF section
   above: nodes, the mesh, accessors, buffer views, the image.
4. **`engine/src/Scene/Model.cpp`**, in this order:
   - `Model::Load`: the steps, top to bottom;
   - `Parse`: the callbacks, the deleter and validation;
   - `LoadMaterials` and `TextureFromImage`: the two ways images come;
   - `LoadMeshes`, `ReadPrimitive` and `ReadFloats`: from accessors to `MeshData`;
   - `ReadTransform`: taking a matrix apart;
   - `Instantiate` and `InstantiateNode`: the recursion.
5. **`engine/include/Viva/MeshRenderer.h`** and `Scene::Render` in
   **`engine/src/Scene/Scene.cpp`**: the parts, all drawn with one world matrix.
6. **`engine/src/Scene/Transform.cpp`**: `Find`.
7. **`engine/src/Core/ImageFile.cpp`** (`DecodeImage`), then `LoadTexture` and `CreateTexture` in
   **`engine/src/Renderer/Renderer.cpp`**: every texture's one way to the GPU.
8. **`cmake/Dependencies.cmake`** (cgltf) and **`sandbox/CMakeLists.txt`**: a `.gltf` model's
   `.bin` and image are listed as assets too, since the `.gltf` only refers to them.

## How to test

1. **Run** the Sandbox. The Stats window shows 24 draw calls, 3842 triangles and 24 GPU
   allocations (about 26 MB). The Scene window lists 45 GameObjects. The log has one line per
   model ("Model loaded", in Debug) and a note that the truck's animation was left out.
2. **Watch:** the truck drives around the pillars, cab first, its wheels rolling. The logo boxes
   ride along on the turning pillars.
3. **Hierarchy:** open "Truck pivot", then "CesiumMilkTruck", "Yup2Zup" and "Cesium_Milk_Truck".
   - Select "Cesium_Milk_Truck": its Mesh Renderer draws 3 meshes.
   - Select "Wheels": its Spinner runs at 400 deg/s. Set it to 0 and the front wheels slide along.
4. **Destroy and shared resources:**
   - Open "Pillar ring" and destroy one "BoxTextured": draw calls drop to 23, but the allocations
     stay at 24, because the other seven boxes use the same mesh and texture.
   - Destroy "Truck pivot": allocations drop to 15 and GPU memory by about 21 MB. The truck was
     the only user of its four meshes and its texture.
5. **Fly** up to the truck (W/A/S/D, right mouse button to look). It's 4.9 m long, 2.8 m wide and
   2.6 m tall: the size of a real one, since glTF works in meters.
6. **Experiments** (rebuild after each, and revert afterwards):
   - Add a second truck in `LoadDemoScene`: `truck->Instantiate(scene)`, then move it with
     `GetTransform().LocalPosition`. The draw calls go up, but the allocations don't.
   - Flip the wheels' axis to `(0, 1, 0)`: the truck moonwalks.
   - Read `CesiumMilkTruck.glb`'s JSON: it's the first chunk of the file, after a 20-byte header. A
     text editor shows it among the binary bytes.
   - Download another model from https://github.com/KhronosGroup/glTF-Sample-Assets (the
     `glTF-Binary` folders hold `.glb` files), copy it to `assets/models/`, list it in
     `sandbox/CMakeLists.txt` and load it. Models that need a glTF extension, like the
     `glTF-Draco` variants, are refused with a message saying which one.

## Known limitations

- **Only the base color is used.** There's no lighting, so metalness, roughness, normal maps,
  occlusion and emission are ignored, and models look flat.
- **No animations, skinning, morph targets, cameras or lights** from the file. A model with
  animations or skins logs that they were left out.
- **Every material is opaque**, and back faces are always culled. glTF's alpha modes (blend,
  mask) and double-sided materials aren't supported yet.
- **Mirrored objects are drawn inside out.** A negative scale, set by a game or by a mirrored node
  in a file, reverses the order of every triangle's corners, so the renderer culls the wrong side.
  Unity flips the culling for such objects automatically. Here, the fix would be choosing the front
  face per draw (Vulkan 1.3 can change it per draw as dynamic state). Neither model is mirrored.
- **A file without a scene** (a library of meshes, in glTF terms) loads, but its instances are
  empty objects.
- **Sampler settings are ignored:** every texture repeats, with trilinear and anisotropic
  filtering. Both models use repeat and linear filtering, so they look as intended.
- **Only the first texture coordinates and vertex colors** (`TEXCOORD_0`, `COLOR_0`) are read, and
  texture transforms (`KHR_texture_transform`) are ignored.
- **Only triangle lists.** Points, lines, strips and fans are skipped with a warning.
- **Required extensions are refused:** compressed meshes (Draco, meshopt) and other image formats
  (KTX2, WebP). Images stored as `data:` URIs inside the JSON aren't supported either.
- **Loading waits for each upload** (M5, M8), one mesh or texture at a time. Load models while
  loading; `Instantiate` is cheap at any time.
