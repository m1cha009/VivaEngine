# M18: Play mode and builds

## What was built

The last step from editing a game to running it: press Play in the editor, and build a folder that
runs without the editor.

- **Play mode**, like Unity's:
  - **Play** (the button in the middle of the menu bar, Ctrl+P, or Edit > Play) starts the scene's
    components (the Spinners turn) and brings the Game view to the front. The menu bar turns blue,
    and the title says `[Playing]`.
  - **Pause** (Ctrl+Shift+P) stops the updates without leaving Play mode.
  - **Stop** (the same button, or Ctrl+P again) puts the scene back exactly as it was before Play.
    Everything changed while playing, by the game or by you, is gone.
  - While playing, changes aren't undo steps and don't count as unsaved, and Save is greyed out.
    New Scene, Open Scene, Close Project, Build and quitting stop Play mode first.
- **Game view:** a new window showing the scene through its own main camera, as the game sees it,
  next to the Scene view and its editor camera. While the mouse is over it, or it has the focus,
  the keyboard and mouse go to the game.
- **VivaPlayer:** a new program (`player/`) that opens the project next to it and plays its startup
  scene in a window. `--project <folder>` plays a project from somewhere else.
- **File > Build...:** asks to save, asks for a folder, and copies into it:
  - VivaPlayer, renamed `<Project>.exe`;
  - the shaders;
  - the project file;
  - `Assets/` and `Scenes/`.

  The folder runs on its own (Unity's Build Settings > Build). From the command line,
  `VivaEditor --open <project> --build <folder>` builds and quits, with exit code 0 on success,
  like Unity's batch-mode builds.
- **Engine additions:**
  - **Render targets** (`Renderer::CreateRenderTarget`, `DrawScene`, `GetTexture`): pictures of the
    scene from their own cameras, in the same frame. They replace M15's single scene target
    (`SetSceneTargetSize`/`GetSceneTexture`) and M16's `DrawGrid`: the grid is now a flag of the
    view, `RenderView::Grid`.
  - `Renderer::SetSceneInWindow` (the editor's window shows only UI).
  - `Application::Quit(exitCode)`.
  - `Application::SetSceneUpdating` is public.
  - `Application::OnRender` is gone; render targets do its job.
  - `CopyFileTo`, `CopyFolderTo`, `GetFileName` and `GetParentFolder` in FileSystem.

## Concepts

### One scene, two cameras: render targets

The Scene view and the Game view show the same scene from two cameras in the same frame. M15's
renderer had a single "scene target" with a single camera, and its notes said this day would come.
Now a game (or the editor) can have any number of **`RenderTarget`s**, Unity's RenderTexture. Each
frame, it calls `DrawScene(target, width, height, view)` for every one it shows. The `RenderView`
gives that picture's camera matrices, background and grid.

In `EndFrame`, the renderer records every target first (into its own color and depth images), then
the window (the UI, which shows the targets' images). The scene's draws were sorted once, and are
recorded once per picture, with a different camera each time.

A target's images are made by `DrawScene` at the size it's given. When the size changes (a window
being resized), new images are made right away. The old ones may still be read by the frames in
flight, so they go through M8's release lists, like any resource the game lets go of.

### Dynamic uniform buffers: a camera per picture

The shaders read the camera from **descriptor set 0** (M6): a uniform buffer per frame in flight.
With several cameras per frame, each picture needs its own camera data. One way would be a buffer
and a set per camera. The engine uses the cheaper, common one:

- Each frame's buffer has a **slot per camera**: slot 0 for the window, then one per target, up to
  four.
- The descriptor is a **dynamic** uniform buffer (`VK_DESCRIPTOR_TYPE_UNIFORM_BUFFER_DYNAMIC`):
  binding the set takes an extra **offset**, which picks the slot.

So one set serves every camera; only the number passed to `vkCmdBindDescriptorSets` changes. The
GPU only accepts offsets that are multiples of its `minUniformBufferOffsetAlignment` (64 or 256
bytes), so each slot is the 128-byte `CameraUniforms` rounded up to that (`FrameUniforms`).

### Play mode is an undo step

Unity's Play mode saves the scene before playing, and restores it on Stop. M17's undo already keeps
the scene's current state as a snapshot (text, with the objects' Ids), so Play mode reuses it:

- **`BeginPlay`** finishes any edit in progress, so the current snapshot is exactly the scene, and
  turns on the components' updates (`Application::SetSceneUpdating(true)`). Their `OnStart` runs
  first, because they never started in Edit mode.
- While playing, `MarkChanged` does nothing: changes made in Play mode aren't undo steps, and don't
  count as unsaved.
- **`EndPlay`** turns the updates off and restores the snapshot (`Scene::Clear` + `Deserialize`).
  Objects the game spawned go with the cleared scene, and the components start fresh next Play. The
  selection stays on the same object if it existed before Play: the Ids again.

Everything that would replace the scene (New, Open, Close Project, Build, Quit) goes through one
function, `AskToSaveThen`, which stops Play mode first. One check covers them all, including
future ones.

### The player and builds

**VivaPlayer** is an Application with no game code at all: it opens a project, sets its assets
folder, loads the startup scene and lets the scene run. Everything the game does comes from the
scene file and the engine's components. (A project's own C++ code comes after M18.)

A **build** is a project folder the player can find. The player looks for a `.vivaproject` next to
itself, so the build is that layout, with the player and the shaders added:

```
MyGame Build/
├── MyGame.exe          VivaPlayer, renamed
├── shaders/            the engine's compiled shaders
├── MyGame.vivaproject  names the startup scene
├── Assets/
└── Scenes/
```

`CopyFolderTo` refuses to copy a folder into itself: a build folder inside `Assets/` would otherwise
copy its own copy, without end. A build folder elsewhere in the project, such as `Builds/` (where
Unity users usually build), is fine.

### Exit codes

`Run()` returns what `Quit(exitCode)` was given: 0 for success, anything else for failure, the way
command-line tools talk to scripts. A batch build that fails, or a player with no project next to
it, exits with 1.

## Reading guide

1. **`engine/src/Renderer/FrameUniforms.h/.cpp`:** the slots and the dynamic descriptor.
2. **`engine/include/Viva/Renderer.h`:** `RenderView`, `CreateRenderTarget`, `DrawScene`,
   `SetSceneInWindow`.
3. **`engine/src/Renderer/Renderer.cpp`:**
   - `TargetImages` and `RenderTarget` at the top;
   - `DrawScene`;
   - in `EndFrame`, the camera slots and the targets' renderings;
   - `RecordTarget`, `RecordRendering` and `RecordDraws` (the dynamic offset).
4. **`editor/src/SceneEditor.cpp`:** `BeginPlay`, `SetPaused`, `EndPlay`.
5. **`editor/src/EditorApp.cpp`:**
   - `Play`, `Stop` and `DrawPlayButtons`;
   - `AskToSaveThen` (stops Play mode);
   - `RunEditCommand`;
   - `ShowBuildDialog`, and the `--build` handling in `OnStart`.
6. **`editor/src/GameView.cpp`**, and **`DrawSceneImage`** in `editor/src/EditorUi.h`, which the
   Scene view shares.
7. **`editor/src/Builder.cpp`**, then **`player/src/PlayerApp.cpp`** and `player/src/Main.cpp`.
8. **`engine/src/Platform/FileSystem.cpp`:** `CopyFolderTo`.

## How to test

1. **Open a project** with the template scene. A **Game** tab sits next to the Scene tab. If the
   editor kept your old layout, the Game window may open floating: use Window > Reset Layout, or
   drag its tab next to Scene.
2. **Play:** click Play (or Ctrl+P). The Game view comes to the front, the cube turns, the menu bar
   turns blue, and the title says `[Playing]`.
3. **Change things while playing:** move the cube with the gizmo in the Scene view, delete the Floor.
   Press **Stop**: the Floor is back, the cube back where it was, and there's no `*`.
4. **Pause:** Play, then Pause. The cube stops, and the title says `[Paused]`. Pause again resumes.
5. **Build:** File > Build..., and pick an empty folder (for example a new `Builds` folder in the
   project). The Console says "Build finished". Open that folder and run `<Project>.exe`. The scene
   plays in its own window, the cube turning.
6. **Command line:**
   ```bash
   VivaEditor --open "C:/path/to/MyGame" --build "C:/path/to/MyGame Build"
   ```
   It builds and quits. Then run the built `.exe`.
7. **The player on its own:**
   ```bash
   VivaPlayer --project "C:/path/to/MyGame"
   ```
   It plays a project straight from its folder.

## Known limitations

- **Game input isn't isolated.** In Play mode, `Input` is shared:
  - Keys and mouse aimed at the Scene view (flying, W/E/R, Del) also reach the game's components.
  - A scene with a FlyCamera flies along with the editor camera.

  Unity only gives the game input while the Game view has focus. The follow-up is a per-window
  input gate for components.
- **One scene per project in the player:** the startup scene. Loading other scenes at runtime comes
  later.
- **A build copies everything** in `Assets/`, used or not, and leaves files already in the build
  folder alone. A build folder inside `Assets/` or `Scenes/` is refused, after the player and
  shaders were already copied there.
- **No build settings:** the window size is the player's default (1280 x 720), and there's no
  fullscreen. The built game has no Esc-to-quit; close the window, as in a Unity player.
- **Up to three render targets per frame:** `FrameUniforms::kMaxViews` is four cameras, and the window
  takes one.
- **The window title** is the project's name; there's no icon.

## Verified on

- **Windows 11 Pro** (RTX 3080 Ti), Debug and Release, zero warnings.
  - **Play mode, driven by posted clicks and keys:**
    - Ctrl+P played: the Game tab came to the front, the cube turned between screenshots, and the
      title said `[Playing]`.
    - The Pause button paused and resumed.
    - Floor, deleted while playing, came back on Stop, with the cube's rotation back to 0 and no
      `*`.
    - File > New Scene while playing stopped Play mode first.
    - Closing the editor while playing quit cleanly.
  - **Builds:**
    - `--build` into a scratch folder and into the project's `Builds/` both succeeded (exit 0).
    - Into the project's `Assets/` it was refused (exit 1), and without a project too.
    - The built `M16.exe` ran on its own: the title is the project name, the cube turns, exit 0.
    - VivaPlayer with `--project` played the demo scene; without a project it exited with 1.
  - **The Sandbox:** drawing into the window through the reworked renderer looks as before, and it
    still round-trips `Demo.scene` byte for byte.
  - **Validation**, including synchronization validation, was silent throughout: two render targets
    a frame, resizing and minimizing while playing.
  - **Not automated:** the native folder dialog of File > Build... (the batch build covers the same
    copying); dragging in Play mode.
