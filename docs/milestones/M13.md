# M13: Scene serialization

## What was built

Scenes can be **saved to a file and loaded back**. It's the first step towards the editor: a
project (M14) is mostly scene files, and the editor (M15–M18) edits them.

- **`Scene::Save(path)` / `Scene::Load(path, assets)`** write and read a **scene file**: JSON text
  with every GameObject, its name, active flag, Transform and components, and its children nested
  inside it. Loading adds the file's objects to the scene (Unity's additive loading).
- **Hand-written JSON** (`engine/src/Core/Json.h`): a value type, a parser that reports errors by
  line and column, and a writer that indents. No new dependency.
- **`Viva/FieldVisitor.h`**: each component lists the fields it saves once, in `VisitFields`. One
  visitor writes them to JSON, another reads them back, and in M16 the Inspector will be a third.
- **`Viva/ComponentRegistry.h`**: component types by name, so `"Spinner"` in a file creates a
  Spinner. The engine's own components are registered; a game registers its own.
- **`Viva/Assets.h`**: every asset by name. Meshes (the built-in primitives and models' meshes),
  textures, models and materials come from here and are shared. Meshes and textures remember their
  names, which is what a scene file writes down.
- **Materials got Unity's Tiling and Offset** (`MaterialSettings::Tiling`, `Offset`).
- **Two new primitives:** `Sphere` and `Cylinder`, sized like Unity's. `Primitives::Plane()` is now
  always 10 × 10 (`Primitives::kPlaneSize`), like Unity's. Scale it for other sizes, and tile its
  texture through the material.
- **`Spinner` moved into the engine** (`Viva/Spinner.h`), so scenes made without code can use it.
- **API changes:**
  - `Renderer::LoadTexture` became `Assets::GetTexture`.
  - `Model::Load(renderer, name)` became `Assets::GetModel(name)`, which returns a `shared_ptr`
    and loads each file once.
  - `CreateMesh` and `CreateTexture` take an optional asset name.
  - `Application::GetAssets()` is new.
  - `GameObject::GetComponents()` and `IsDestroyed()` are new.
  - `Primitives::Plane(width, length, repeats)` became `Primitives::Plane()`.
- **Sandbox:**
  - `--save <file>` saves the scene once it's built, and `--load <file>` shows a scene file instead
    of the game.
  - The demo scene now uses only assets (its pillars are plain cubes with colored materials).
  - The Lane Runner's road and grass are the built-in plane, scaled, with tiled materials.
  - `TruckWheels` turns the axles itself instead of adding a Spinner to each (see "Runtime state
    stays out of the file" below).
  - Two example scenes are in `assets/scenes/`: `Demo.scene`, which `--demo --save` wrote, and
    `Shapes.scene`, written by hand.

## Concepts

### Serialization

*Serializing* means turning objects in memory into a stream of bytes or text that can be stored
and turned back into the same objects later (*deserializing*). Unity does it all the time: saving
a scene, saving a prefab, entering Play mode, showing the Inspector. You rarely notice, because C#
can do it by itself.

Memory holds things a file can't: pointers, GPU handles, `shared_ptr`s. A file can only hold
numbers and text. So serializing is mostly deciding **what each thing becomes in the file**:

| In memory | In the scene file |
|---|---|
| a `GameObject` with children | a JSON object with a `"Children"` array nested inside it |
| the parent pointer | nothing: being nested inside the parent says it |
| `glm::vec3`, `glm::quat` | `[x, y, z]`, `[x, y, z, w]` |
| a component | `{ "Type": "Spinner", ...its fields... }` |
| `shared_ptr<Mesh>` (GPU buffers) | the mesh's asset name, `"Primitives::Cube"` |
| `shared_ptr<Material>` | the material's settings: texture name, color, tiling, offset |
| runtime state (`TruckWheels::m_Axles`) | nothing: `OnStart` finds it again |

### JSON

JSON is a text format with six kinds of values: `null`, `true`/`false`, numbers, strings in
quotes, arrays `[ ... ]` and objects `{ "name": value, ... }`. A scene file looks like this:

```json
{
  "Format": "VivaEngine Scene",
  "Version": 1,
  "GameObjects": [
    {
      "Name": "Crate",
      "Active": true,
      "Transform": { "Position": [0, 1.5, 0], "Rotation": [0, 0, 0, 1], "Scale": [1.2, 1.2, 1.2] },
      "Components": [
        { "Type": "MeshRenderer", "Parts": [ { "Mesh": "Primitives::Cube",
          "Material": { "Texture": "textures/crate.png", "Color": [1, 1, 1, 1], "Tiling": [1, 1], "Offset": [0, 0] } } ] },
        { "Type": "Spinner", "Axis": [0.4, 1, 0.2], "DegreesPerSecond": 46 }
      ],
      "Children": [ ... ]
    }
  ]
}
```

Unity writes its scenes as text too (YAML, a cousin of JSON), for the same reasons: you can read
them, diff them in git, and fix them by hand.

**How `Json.cpp` works:**
- `Json` holds one value of any kind in a **`std::variant`**: a type-safe union, a box that holds
  exactly one of the listed types and knows which. `AsNumber()` and friends return a pointer to the
  value, or `nullptr` if it's another kind. That's like C#'s `as` operator.
- `Json::Object` is a `std::vector` of name/value pairs rather than a `std::map`, so members stay
  in the order they were added: a saved file lists `"Name"` before `"Transform"`.
- The parser is **recursive descent**: one function per kind of value (`ParseObject`,
  `ParseArray`, `ParseString`...), each calling the others for what's inside it. The code follows
  the JSON grammar closely.
- **No exceptions:** the first error is recorded with its line and column, and every function
  returns an empty `std::optional` from then on, back up to the caller. A broken file gives a
  message like `line 4, column 3: expected ',' or '}'`.
- **Numbers** use C++17's `std::from_chars` and `std::to_chars`. They're fast, and unlike `printf`
  they don't depend on the PC's language settings (some write `0,5`). `to_chars` writes the
  shortest text that reads back as exactly the same number.
- **Floats:** the scene's numbers are `float`s, but JSON numbers are stored as `double`s. A float
  holds 0.1 as 0.100000001490116..., which as a double prints with all those digits.
  `FloatToJsonNumber` converts through the float's shortest text, so the file says `0.1`.

### The visitor pattern: one list of fields for every job

In C#, Unity finds a MonoBehaviour's public fields by itself through **reflection**: code that asks
at runtime "which fields does this class have?". C++ has no reflection, so each component lists
its fields once:

```cpp
void Spinner::VisitFields(FieldVisitor& fields)
{
    fields.Field("Axis", Axis);
    fields.Field("DegreesPerSecond", DegreesPerSecond);
}
```

A `FieldVisitor` receives each field's **name and a reference to it**, and decides what to do:

- `JsonFieldWriter` (saving) reads the value and adds it to a JSON object.
- `JsonFieldReader` (loading) looks the name up in a JSON object and writes the value into the
  field.
- In M16, an `InspectorVisitor` will draw an ImGui widget per field, which edits it directly.

A material isn't a component, but it has fields too. `VisitFields(FieldVisitor&, MaterialSettings&)`
(in `Scene/FieldVisitor.cpp`) lists them once: Texture, Color, Tiling, Offset. Each visitor's
material overload just opens a nested object and calls it.

The component doesn't know which job is running; the visitor doesn't know which component it's
visiting. This is the **visitor pattern**, and Unreal Engine's `Serialize(FArchive&)` works the
same way. The alternative, a `Save()` and a `Load()` per component, would let the two drift apart
(a field saved but never loaded).

`Field` is a set of **virtual function overloads**, one per type (`float&`, `glm::vec2&`,
`glm::vec3&`, `glm::quat&`, `std::shared_ptr<Mesh>&`, `std::shared_ptr<Texture>&`...). The compiler picks the right one from the field's type.
Lists use `List(name, vector, lambda)`, a template, because virtual functions can't be templates.
It's built on four small virtual functions (`BeginList`, `BeginElement`...).

Rules that make old and new files keep working:
- A field the file doesn't have **keeps its value**: the default from the component's constructor.
  `{ "Type": "Spinner" }` is a valid Spinner.
- A field the code doesn't know is **ignored**.
- A field of the wrong type keeps its value and logs a warning.

So adding a field to a component doesn't break old scene files, as in Unity.

### The component registry: names to types

A file says `"Type": "Spinner"`. Loading needs to turn that text into `AddComponent<Spinner>()`,
and saving needs the reverse: from a component, its name. C# would ask reflection. In C++, each
type is registered once:

```cpp
ComponentRegistry::Register<FlyCamera>("FlyCamera");
```

- `Register<T>` stores the name, `typeid(T)` (the type's runtime identity, like C#'s
  `System.Type`), and a **factory**: `&Create<T>`, a pointer to the version of the small template
  function `Create` that does `gameObject.AddComponent<T>()` for T.
- `NameOf(component)` compares `typeid(component)` with the stored types. For a class with virtual
  functions, `typeid` of a reference gives the object's **real** type (Spinner), not the
  reference's (Component).
- The list lives in a **function-local static**, created the first time it's used. A global variable
  would be created at an unspecified time before `main`, possibly after another file's code had
  already tried to use it. The engine's own types are registered through the same `Register<T>`, on
  the registry's first use (`RegisterEngineComponents`).
- **Why not have each component register itself** from a global in its own .cpp file? Because the
  engine is a static library: the linker copies only the object files something uses into the
  .exe. A file nobody calls would be dropped, and its registration with it, silently. That's a
  classic C++ trap, so registration is explicit.

Unregistered components are skipped when saving, with a warning naming the type. The Lane Runner's
components aren't registered: that game is built in code.

### Asset names: how a file refers to GPU resources

A `shared_ptr<Mesh>` is a GPU buffer; a file can't hold it. Unity solves this with **asset
references**: a scene stores the GUID of the mesh asset, not the mesh. VivaEngine uses names:

| Asset | Name |
|---|---|
| built-in primitive | `Primitives::Cube`, `Primitives::Plane`, `Primitives::Sphere`, `Primitives::Cylinder` |
| a model's mesh | `models/CesiumMilkTruck.glb#mesh2/0` (mesh 2, primitive 0, as numbered in the file) |
| an image file | `textures/crate.png` |
| an image inside a model | `models/CesiumMilkTruck.glb#image0` |
| a model | `models/CesiumMilkTruck.glb` |

- **Every mesh and texture remembers its name** (`Renderer::GetAssetName`). `Assets` gives them
  their names when it creates them. Saving writes the name; loading asks `Assets` for it.
- **`Assets` is the one place that turns names into assets.** Before M13, `Renderer::LoadTexture`
  and `Model::Load` each did part of that job. That was a deferral from M7: "loading APIs resolve
  asset names in one place". Now the renderer only makes GPU resources from data, and `Assets`
  knows about files and names.
- **Materials have no names:** a material *is* its settings. A scene file writes the settings, and
  loading asks `Assets::GetMaterial(settings)`, which returns an existing material with equal
  settings if there is one. So the eight logo boxes, or a hundred cubes placed in the editor, share
  one material. `MaterialSettings` compares with C++20's **defaulted `operator==`**, which the
  compiler writes for you, comparing field by field.
- **Caching:** primitives, textures and materials are remembered through `std::weak_ptr`s, so an
  asset nobody uses any more is freed. Models are kept with `shared_ptr`s until the application
  ends, because they're slow to load and get instantiated again and again. (Unity frees unused
  assets on `Resources.UnloadUnusedAssets`; that would be the next step.)
- **Things made in code have no name.** The Lane Runner's road texture is generated pixels, and a
  file can't refer to it, just as Unity can't save a mesh a script created unless you save it as an
  asset first. Saving warns and leaves it out.

### Runtime state stays out of the file

A scene file should hold the scene **as it was built**, not things components add while the game
runs. In M11, `TruckWheels` added a Spinner to each axle in `OnStart`. Saved after that, a scene
would hold those Spinners, and loading it would start `TruckWheels` again, which would add two
more. Now `TruckWheels` turns the axles itself, with the same quaternion step a Spinner uses, so it
changes nothing but rotations. The rule of thumb: a component may *find* other objects in
`OnStart` (and keep pointers to them), but shouldn't build scene content there that a file would
then also hold.

### Tiling and offset

A Unity material has Tiling and Offset for its texture, and now ours does too: the vertex shader
computes `uv * Tiling + Offset`. They travel as push constants, next to the model matrix and the
color (96 bytes of the 128 every GPU guarantees). The demo's floor is the built-in 10 × 10 plane
scaled 2.8×, with the checker texture tiled 14×. Before M13 it was a 28 × 28 mesh made in code with
the repeats baked into its UVs, which a scene file couldn't refer to. `Primitives::Plane` lost its
size and repeat parameters, so there's one way to tile a texture: the Lane Runner's road and grass
are scaled planes with tiled materials too.

### Sphere and cylinder

Both are built as a **grid of vertices** wrapped around the Y axis (`AddGrid` in `Primitives.cpp`):
- The **sphere** has 17 rings from the top pole to the bottom, of 33 vertices each. The last vertex
  of a ring sits on the first, with U = 1 instead of 0: that's the **seam** where the texture's
  right edge meets its left. The poles' rows collapse to one point, which leaves some empty
  triangles there: harmless, and it keeps the code short.
- The **cylinder** is a two-row grid for its side, plus a **cap** at each end: a center vertex and
  a fan of triangles. The caps need their own vertices: they sit where the side's edge vertices
  are, but with different texture coordinates. (The cube's corners are repeated for the same
  reason.)
- The winding (counter-clockwise front faces) was checked the practical way: with back faces
  culled, a wrongly wound shape shows its inside or disappears.

### Lossless round trips

Save → load → save gives a **byte-identical file**. Two details make that true:
- `FloatToJsonNumber` writes each float's shortest exact text, so reading it back gives the same
  float.
- Rotations read from a file are normalized only if their length is visibly off 1 (a file edited
  by hand). Normalizing every time changed the last digit of some quaternions, so every save would
  have rewritten them.

## Reading guide

1. **`assets/scenes/Shapes.scene`**, then a bit of **`assets/scenes/Demo.scene`**: what a scene
   file looks like, hand-written and saved.
2. **`engine/include/Viva/FieldVisitor.h`**, then the `VisitFields` functions in
   **`engine/src/Scene/Spinner.cpp`**, **`Camera.cpp`**, **`Transform.cpp`**,
   **`engine/include/Viva/MeshRenderer.h`** (a list) and **`engine/src/Scene/FieldVisitor.cpp`**
   (a material's settings).
3. **`engine/include/Viva/ComponentRegistry.h`** and **`engine/src/Scene/ComponentRegistry.cpp`**:
   `typeid`, `&Create<T>` as the factory, the function-local static.
4. **`engine/src/Core/Json.h`**, then **`Json.cpp`**: `Parser` from `ParseDocument` down, `Fail`
   for errors, then `WriteValue`.
5. **`engine/src/Scene/SceneFile.cpp`**: `JsonFieldWriter`, `JsonFieldReader`, then
   `SaveGameObject`/`LoadGameObject` (recursion again, as in `Model::Instantiate`), then
   `Scene::Save` and `Scene::Load` at the bottom.
6. **`engine/include/Viva/Assets.h`** and **`engine/src/Scene/Assets.cpp`**: names, caches,
   `weak_ptr` vs `shared_ptr`.
7. **`engine/src/Scene/Model.cpp`**: `LoadMeshes` and `TextureFromImage` naming what they make;
   `FindMesh`/`FindTexture`.
8. **`engine/include/Viva/Renderer.h`**: `MaterialSettings` (Tiling, Offset, `operator==`), asset
   names on `CreateMesh`/`CreateTexture`, `GetAssetName`/`GetSettings`. Then `shaders/Unlit.vert`.
9. **`engine/src/Core/Primitives.cpp`**: `CirclePoint`, `AddGrid`, `Sphere`, `Cylinder`, `AddCap`.
10. **`sandbox/src/Main.cpp`** (registration, `--save`/`--load`), **`sandbox/src/DemoScene.cpp`**
    (everything through `Assets`) and **`sandbox/src/TruckWheels.cpp`** (turning the axles).

## How to test

1. **Save the demo:** run `Sandbox --demo --save my.scene`. The log says "Scene saved", with no
   warnings. Open `my.scene` in a text editor (it's in the working folder: in CLion, the folder the
   run configuration starts in).
2. **Load it:** `Sandbox --load my.scene`. It looks like `--demo`: the Stats window shows the same
   24 draw calls, 3842 triangles and 24 allocations, and the Scene window 45 GameObjects. The truck
   drives, the wheels roll, the ring turns. All of that comes from the file.
3. **The examples:** from the build's `bin` folder (or the packaged folder), run
   `Sandbox --load assets/scenes/Shapes.scene` for the sphere, cylinder, cube and plane, and
   `Sandbox --load assets/scenes/Demo.scene` for the demo.
4. **Edit by hand** (a copy of `Shapes.scene`), then load it:
   - Change a `"Position"`, a `"Color"` or `"DegreesPerSecond"`.
   - Change the sphere's `"Tiling"` to `[8, 4]`.
   - Delete a field: it gets its default. Delete `"Transform"` entirely: the object sits at the
     origin.
   - Add a GameObject with a `"Primitives::Cylinder"` mesh, or nest one inside another's
     `"Children"`.
   - Break it: remove a comma. The log names the line and column. Write `"Scale": "big"`: a
     warning, and the scale stays 1. Write `"Type": "Rigidbody"`: a warning, and the rest loads.
5. **Save the Lane Runner:** `Sandbox --save lane.scene`. The log warns about everything a file
   can't hold: the game's unregistered components, and the road's and grass's meshes and textures
   made in code.
6. **Round trip:** `Sandbox --load my.scene --save again.scene`, then compare the two files: they're
   identical.

## Known limitations

- **No asset GUIDs.** A scene refers to assets by path, so renaming or moving an asset breaks the
  scenes that use it. Unity's `.meta` files solve this (see "Later" in `docs/EditorRoadmap.md`).
- **A model's meshes are named by their index in the file.** If the model file changes (meshes
  added or reordered), scenes may point at the wrong mesh.
- **Model instances are saved as plain GameObjects**, node by node, not as "an instance of this
  model". Unity's prefab instances remember their prefab, and changes to the prefab reach them.
- **References between objects aren't saved.** A component that points at another GameObject
  (`FollowCamera`'s target, `LaneRunner`'s truck) has nothing to write; it must find the object
  again in `OnStart`, by name with `Transform::Find`.
- **Components register by hand.** Forgetting to register one means it's skipped on save, with a
  warning.
- **Materials are saved by value.** Two objects that shared one material share it again after
  loading (equal settings), but there's no named material asset to edit in one place.
- **The camera's field of view is saved in radians**, like the field.
- **Loading is additive.** To replace the scene, it has to be emptied first; there's no
  `Scene::Clear` yet (M15 will need one).
