# M4: First triangle

## What was built

The engine draws geometry: the classic RGB triangle, red at the top, green bottom-right and blue
bottom-left, with the colors blended across it. It sits on the slowly cycling background from M3,
now darker.

- **Shaders.**
  - `shaders/Triangle.vert` places three hardcoded vertices.
  - `shaders/Triangle.frag` colors each pixel.
  - The build compiles both to SPIR-V (`viva_compile_shaders(VivaEngine …)` in
    `engine/CMakeLists.txt`). They're engine shaders, so the engine target owns them.
- **`Pipeline`** (`engine/src/Renderer/Pipeline.h/.cpp`): loads the two `.spv` files and bakes
  them, plus all the fixed-function settings, into a `VkPipeline`. It uses
  `VkPipelineRenderingCreateInfo` (dynamic rendering, no render pass) and dynamic viewport and
  scissor.
- **`FileSystem`** (`engine/src/Platform/`): finds the executable's folder (through SDL) and reads
  files. The shaders are loaded from `shaders/` next to the executable.
- **`DrawFrame`** now binds the pipeline, sets the viewport and scissor, and calls
  `vkCmdDraw(cmd, 3, 1, 0, 0)` inside the dynamic-rendering block.
- **`ApplicationSettings::Display`** and the sandbox's `--display <n>`: which monitor the window
  opens on. Automated test runs use it to stay on the second screen while the main one is busy.

## Concepts

### Shaders: small programs that run on the GPU

Shaders are written in **GLSL**, a C-like language. HLSL, which Unity shaders use, is a close
cousin. Vulkan never sees the GLSL text: the build compiles it to **SPIR-V**, a compact binary
format, with `glslc` (M0's `viva_compile_shaders` function, used here for the first time). A typo
in a shader is therefore a *build* error, with a file and line number.

- **The vertex shader** (`Triangle.vert`) runs once per vertex. It outputs `gl_Position`, the
  vertex's position in **clip space**. There are no vertex buffers yet (M5), so it picks
  positions from a constant array using `gl_VertexIndex` (0, 1, 2).
- **The fragment shader** (`Triangle.frag`) runs once per pixel the triangle covers (a
  "fragment"), and writes that pixel's color.
- **Varyings**: whatever the vertex shader outputs (`layout(location = 0) out vec3 outColor`) is
  **interpolated** across the triangle before the fragment shader reads it (`in vec3 inColor`).
  That's where the smooth blend between the three corner colors comes from.

### Clip space, and why Y points down

Clip space is the square the GPU maps onto the viewport: x from −1 (left) to +1 (right) and y from
−1 to +1. In **Vulkan, y = −1 is the top**. In OpenGL it's the bottom, which is why OpenGL
tutorials look upside down when ported. So the top corner is `(0, -0.5)`. Clip space is always
that square whatever the window's shape, so a wide window stretches the triangle. M6's projection
matrix accounts for the aspect ratio.

### The graphics pipeline

A **`VkPipeline`** bakes *everything* about how to draw into one object:
- the shader stages;
- the input layout (no vertex buffers yet);
- the primitive type (triangle list);
- rasterization (fill, no culling);
- multisampling (one sample);
- blending (off);
- the format of the image it draws into.

In Unity terms, it's a compiled shader pass with its render state ("Cull Off", "Blend Off",
"ZWrite …") fixed in. Vulkan wants it all up front so the driver can compile the final GPU code
once, at load time, instead of patching shaders in the middle of a frame (the cause of many
"shader compilation stutters" in older APIs).

A few states can stay **dynamic**, set while recording instead of baked in. We make the
**viewport** (which part of the image clip space maps to) and the **scissor** (pixels outside it
are dropped) dynamic, so resizing the window doesn't require rebuilding the pipeline.

The **pipeline layout** describes what the shaders receive besides vertices: descriptor sets
(textures, buffers) and push constants. It's empty for now; M6 fills it with the camera and model
matrices.

With dynamic rendering, the pipeline doesn't reference a render pass. It just states the format of
the image(s) it will draw into (`VkPipelineRenderingCreateInfo`). That's why the swapchain's format
must not change when it's rebuilt, which `RecreateSwapchain` asserts since M3's cleanup.

### Shader modules

`vkCreateShaderModule` wraps the SPIR-V bytes so the pipeline can use them. Once the pipeline is
built, it has its own compiled copy, so the modules are destroyed right away.

### Finding files at runtime

The shaders are compiled into `build/<preset>/bin/shaders/`, next to the executable, and
`scripts/package.cmd` copies them into `dist/M4/shaders/`. The engine looks for them relative to
**the executable's folder**, which SDL reports, not the current working directory. That way the
game works whether it's started from CLion, a terminal or Explorer.

## Reading guide

1. **`shaders/Triangle.vert`** and **`shaders/Triangle.frag`**: short, and heavily commented.
   Notice `gl_VertexIndex`, `gl_Position` and the `location = 0` pairing.
2. **`engine/CMakeLists.txt`** (the end): `viva_compile_shaders(VivaEngine …)`. Then look in
   `build/windows-debug/bin/shaders/` for the `.spv` files.
3. **`engine/src/Renderer/Pipeline.h`** and **`Pipeline.cpp`**: `PipelineSettings`, filled with
   designated initializers like `ApplicationSettings`. `Create()` reads top to bottom as the list
   of pipeline states; notice the dynamic viewport and scissor, `VkPipelineRenderingCreateInfo`,
   and `CompiledShaderPath`, the one place that knows where compiled shaders live.
4. **`engine/src/Platform/FileSystem.h`** and **`FileSystem.cpp`**: `GetExecutableDirectory()` and
   `ReadBinaryFile()`. Notice `SDL_LoadFile`, which handles UTF-8 paths on every OS and explains
   failures through `SDL_GetError()`, and the `std::optional` result.
5. **`engine/src/Renderer/Renderer.cpp`**: the pipeline built in `Create()`. In `DrawFrame()`,
   viewport and scissor are set once after `vkCmdBeginRendering`. Then `RecordDraws()` binds the
   pipeline and draws: that's the function later milestones grow.

## How to test

1. **Run** the Sandbox. A centered RGB triangle sits on a dark, slowly changing background.
2. **Resize** the window. The triangle stretches with it: viewport and scissor follow every new
   swapchain size, and no validation messages appear.
3. **`--display 1`** opens the window on your second monitor.
4. **RenderDoc**: capture a frame and select `vkCmdDraw`. The *Mesh Viewer* shows the three
   vertices, and the *Pipeline State* tab shows every state from `Pipeline.cpp`.
5. **Experiments** (rebuild after each, and revert afterwards):
   - Change a color in `Triangle.vert` (for example `vec3(1.0, 1.0, 0.0)` for yellow). The build
     recompiles only that shader.
   - Introduce a typo in `Triangle.frag`. The *build* fails with the file and line.
   - Flip the y values in `kPositions`. The triangle turns upside down.
   - In `Pipeline.cpp`, set `.polygonMode = VK_POLYGON_MODE_LINE`. Wireframe needs the
     `fillModeNonSolid` device feature, so the validation layer tells you exactly that.

## Known limitations

- The vertices live in the shader, so there's nothing to load or animate yet (M5: vertex and
  index buffers).
- One hardcoded pipeline in the renderer. M8 introduces `Shader`/`Material` and moves what's drawn
  into the sandbox.
- No depth testing or culling yet (M6).
