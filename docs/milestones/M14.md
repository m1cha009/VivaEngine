# M14: Projects and the Project Manager

## What was built

The engine now has **projects**, and a second program, **VivaEditor**, that creates, lists, opens
and deletes them, like Unity Hub.

- **A project is a folder** (`Viva/Project.h`):

  ```
  MyGame/
  ├── MyGame.vivaproject   JSON: name, engine version, startup scene
  ├── Assets/              the project's textures, models... (asset names start here)
  └── Scenes/
      └── Main.scene       a scene file (M13), the one that opens first
  ```

  `Project::Create(parentFolder, name, error)` makes one from a template: a camera, a floor and a
  turning cube. `Project::Open(folder, error)` reads one and checks it.
  `Project::CheckNewProject(parentFolder, name)` says why a project can't be created there, which
  the New Project popup shows while you type.
- **VivaEditor** (`editor/`), a new executable next to the Sandbox:
  - It starts in the **Project Manager**: the list of projects (name, location, when last opened,
    newest first), **New Project**, **Add Existing...**, and per project **Open**, **Remove** (from
    the list only) and **Delete...** (from disk, after a confirmation that names the folder).
  - Missing projects (folder moved or deleted) are greyed out and can only be removed.
  - **New Project** suggests an unused name ("My Project", "My Project 2"...) in the location
    used last time (first time: `Documents/VivaEngine Projects`), with **Browse...** for the OS
    folder picker. Problems (a bad name, a folder that exists) show while typing.
  - **Opening** a project shows its startup scene with a fly camera (looking only: editing is
    M15–M17), and a small panel with **Close Project**, which goes back to the list.
  - The list lives in `%APPDATA%\Viva\VivaEditor\projects.json`.
- **Engine additions:**
  - **`Viva/FileSystem.h` is public**, and bigger: read and write files, check paths, create, list
    and delete folders, the user's settings and Documents folders, and **`ShowFolderDialog`**, the
    OS's folder picker. It's built on SDL (in `Platform/`, like all OS code).
  - **`Viva/Json.h` is public**: the editor writes its list with it. `ReadJsonFile(path, format,
    version, error)` reads, parses and checks the header of scene files, project files and the
    project list in one place.
  - **`Assets` has a root folder**, and `Application::SetAssetsFolder(folder)` swaps it. Names start
    next to the executable, as before, until the editor points them at an open project's `Assets`
    folder.
  - **`ApplicationSettings::QuitAfter`** and **`ReadCommandLine`**: `--display`, `--no-vsync` and
    `--quit-after` are read and handled by the engine for every program, instead of each `main`.
  - **`Scene::Clear()`** destroys every GameObject, for switching scenes.
  - **`FlyCamera` moved into the engine** (`Viva/FlyCamera.h`) and is registered as a built-in
    component, because both programs use it.

## Concepts

### Two programs, one engine

`VivaEngine` is a static library, and now two executables link it: the Sandbox (the game) and
VivaEditor (the tool). Neither contains engine code; each is a few files that use it. That's the
point of making the engine a library from M0. Unity works the same way: the Unity editor and every
game you build share one engine, the runtime.

The editor is an `Application` like any game: `OnStart` loads the project list, and `OnUpdate`
draws either the Project Manager or the open project's panel. Its "game" is projects.

### Projects: folders, not databases

A project is just a folder with a known layout and a small JSON file saying "this is a project".
Everything else comes from that:
- **Asset names** start in the project's `Assets` folder, so `"textures/crate.png"` means
  `MyGame/Assets/textures/crate.png`. `Assets` takes its root folder in its constructor, and
  `Application::SetAssetsFolder` replaces the application's `Assets` with a fresh one for each
  project the editor opens, so nothing loaded for one project leaks into the next.
- **The startup scene** is named in the project file, relative to the project folder.
- **The engine version** is written into the project file when it's created. Opening a project
  made with another version logs a warning but opens it anyway, like Unity's "this project was
  made with another version" notice.
- **Moving or renaming** the folder doesn't break the project: nothing inside it stores its own
  path. The editor's list does, so it shows the old entry as missing; **Add Existing** (or opening
  the new location) brings it back.

`Project` is a plain value class: it describes a folder and owns no resources, so copying it is
fine, and `std::optional<Project>` is "maybe a project". Unity's Hub works the same way: a project
is a folder, and the Hub keeps a list of paths.

### The project list: settings that belong to the user

The list of projects isn't part of any project: it's the user's, on this computer. Every OS has a
place for such settings: `%APPDATA%` on Windows, `~/Library/Application Support` on macOS.
`GetUserDataFolder("Viva", "VivaEditor")` asks SDL for it, which creates
`%APPDATA%\Viva\VivaEditor\`. The list is a JSON file there:

```json
{
  "NewProjectLocation": "C:/Users/Michail/Documents/VivaEngine Projects",
  "Projects": [
    { "Name": "MyGame", "Folder": "C:/Users/Michail/Documents/VivaEngine Projects/MyGame", "LastOpened": 1791124752 }
  ]
}
```

- **`LastOpened` is Unix time:** seconds since 1 January 1970, UTC, which is how most programs
  store a moment. Since C++20, `std::chrono::system_clock` counts from that date.
- **"5 minutes ago"** is shown instead of a date, like Unity Hub. A relative time needs no time
  zone, which keeps the code simple.
- **Paths are normalized** (`NormalizePath`): `/` separators and no trailing `/`, so two spellings
  of one folder compare equal as text.

### Immediate mode UI

The Project Manager is Dear ImGui, which is **immediate mode**: there are no button objects. Every
frame, `Draw()` calls `ImGui::Button("Open")` again for each row, and it returns `true` in the frame
it's clicked. The screen is a function of the data: the list changes, and the next frame shows it.
Unity's old `OnGUI` (and its editor's `EditorGUILayout`) works the same way. uGUI and UI Toolkit are
**retained mode**: you create widgets once, and keep them in sync with your data.

A few ImGui ideas appear for the first time:
- **IDs:** ImGui tells widgets apart by their label. Every row has an "Open" button, so each row
  pushes its own ID scope (`PushID(folder)`).
- **Modal popups** (New Project, Delete, Problem) block the rest of the UI until closed. They're
  opened with `OpenPopup`, called from the same place in the UI as `BeginPopupModal`; hence the
  `m_OpenNewProject` flags, which open them in the next frame.
- **Text fields** edit a `char` buffer the caller owns (`std::array<char, 512>`), terminated by
  `'\0'`: ImGui is C-style here.
- **Disabled widgets** (`BeginDisabled`) are drawn greyed out and ignore clicks: that's how a
  missing project's Open button works.

### The folder dialog: a callback from another thread

`ShowFolderDialog(title, startFolder, onChosen)` opens Windows' folder picker without stopping the
game loop. SDL reports the choice through a C callback, **possibly on another thread**. Game code
running on two threads at once is a classic source of bugs, so the engine never lets that reach
the game:

1. The SDL callback (`OnDialogClosed`, maybe on SDL's thread) only appends the result to a list,
   guarded by a **`std::mutex`**. A mutex is a lock: whoever holds it is the only one touching the
   list, like C#'s `lock` statement. `std::lock_guard` takes it and releases it when it goes out of
   scope, which is RAII again.
2. `Window::PollEvents`, on the main thread, calls `DeliverFolderDialogResults()`. It takes the
   results out under the lock, then calls each `onChosen` without it.

So `onChosen` runs on the main thread, during a frame, like any other input. The request travels
through SDL as a `void*` "userdata" pointer: released from its `unique_ptr` before the call, and
taken back into one in the callback. That's the usual way to pass C++ state through a C API.

### Deleting for good, carefully

**Delete...** removes the project folder and everything in it, permanently: `DeleteFolder` uses
SDL's `SDL_RemovePath`, which doesn't use the Recycle Bin. Because that can't be undone:
- The confirmation popup names the full path.
- Just before deleting, the folder is checked again for its `.vivaproject` file. A list entry that
  has come to point at some other folder can't delete it.
- Missing projects can't be deleted (there's nothing there), only removed from the list.

SDL only removes empty folders, so `DeleteFolder` empties a folder first, calling itself for each
subfolder: recursion, as in `Model::Instantiate`.

### Why SDL instead of std::filesystem

C++17's `std::filesystem` does all of this too. The engine uses SDL's file functions instead
because:
- Every `std::filesystem` call either throws exceptions (which the engine doesn't use) or needs an
  `std::error_code` argument.
- On Windows, `path::string()` can throw for names that aren't plain ASCII (decision log, M4).
- SDL takes UTF-8 everywhere and is already the engine's platform layer.

### Raw string literals

The template scene for new projects is written in `Project.cpp` as a **raw string literal**:
`R"(...)"`. Everything between `R"(` and `)"`, quotes and line breaks included, is the text as it
stands, with nothing to escape. It's C#'s `@"..."` (or `"""..."""`).

## Reading guide

1. **`engine/include/Viva/Project.h`**, then **`engine/src/Core/Project.cpp`**: the folder layout,
   `CheckName`, the template scene, `Create` (and its clean-up on failure), `Open`.
2. **`engine/include/Viva/FileSystem.h`**, then **`engine/src/Platform/FileSystem.cpp`**:
   `NormalizePath`, `ListFolder` (a C callback with userdata), `DeleteFolder` (recursion).
3. **`engine/src/Platform/FolderDialog.cpp`**: the mutex, `OnDialogClosed` on SDL's thread, and
   `DeliverFolderDialogResults` on the main thread (called from `Window::PollEvents`).
4. **`editor/src/Main.cpp`** and **`editor/src/EditorApp.cpp`**: the editor as an `Application`;
   `OpenProject` (`Clear`, `SetAssetsFolder`, `Scene::Load`, a FlyCamera) and `CloseProject`.
5. **`editor/src/ProjectList.cpp`**: the list file, Unix time, sorting.
6. **`editor/src/ProjectManager.cpp`**: `Draw`, the table (`PushID`, `BeginDisabled`), and the three
   popups.
7. Smaller changes: `ReadJsonFile` (`engine/src/Core/Json.cpp`), `Assets`' root folder and
   `Application::SetAssetsFolder`, `ApplicationSettings::ReadCommandLine`, `Scene::Clear`, and
   `Viva/FlyCamera.h`, which moved from the sandbox.

## How to test

1. **Build** as usual. `build\windows-debug\bin\` now has `VivaEditor.exe` next to `Sandbox.exe`;
   in CLion, pick the **VivaEditor** run configuration.
2. **First run:** the list is empty. Click **New Project**: the name is "My Project" and the
   location `Documents/VivaEngine Projects`. Try typing a bad name (`a:b`, `CON`, a trailing dot)
   and watch the message; try **Browse...**. Click **Create**: the project opens on a sky-blue
   background with a floor and a turning orange cube. Fly around (W/A/S/D, right mouse button).
3. **Look at the folder** in Explorer: `My Project.vivaproject`, `Assets`, `Scenes/Main.scene`.
   Both files are readable JSON.
4. **Close Project**, create a second one ("My Project 2" is suggested), close it, then **close the
   editor and start it again**: both projects are listed, newest first, with "N minutes ago".
5. **Open** the first one: it moves to the top.
6. **Delete...** the second one: the popup names its folder. Confirm: it's gone from the list and
   from the disk.
7. **Missing:** close the editor, rename a project folder in Explorer, start the editor: the
   project is greyed out with "(missing)". **Add Existing...** and pick the renamed folder: it's
   back (under its new path). Remove the stale entry.
8. **Your own assets:** copy `assets/models` and `assets/textures` from the repo into a project's
   `Assets` folder, and `assets/scenes/Demo.scene` into its `Scenes` folder. Change
   `"StartupScene"` in the `.vivaproject` file to `"Scenes/Demo.scene"`, and open the project: the
   demo scene, from the project's own assets. The log warns that `TruckWheels` isn't known (it's
   the Sandbox's), so the wheels stand still.
9. **A broken project:** edit the `.vivaproject` file into invalid JSON and open it: the Problem
   popup says where it's broken.

## Known limitations

- **Nothing in a project can be edited yet**, and nothing is saved back: the editor only views
  scenes. M15 adds the editor's windows and its own camera; M16 the editing.
- **The fly camera is added to the scene's camera** when a project opens. M15 replaces it with an
  editor camera that isn't part of the scene.
- **Only the startup scene opens.** Opening other scenes comes with M15's File menu.
- **Projects can't hold C++ code** (decided: data only first). Their components are the engine's
  built-in ones: MeshRenderer, Camera, Spinner, FlyCamera.
- **The list notices missing folders** when the editor starts and when a project closes, not
  while you look at it.
- **No project templates or thumbnails**, unlike Unity Hub, and no "open with another engine
  version".
- **A folder dialog still open when the editor quits** is left to the OS.
