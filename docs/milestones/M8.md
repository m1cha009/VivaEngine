# M8: Renderer abstraction

## What was built

The scene looks the same as in M7, but the engine no longer decides what to draw: the sandbox
does, through a public renderer API. The renderer turns into a service the game uses, like
Unity's `Graphics` and its Mesh, Texture and Material assets.

- **`Viva/Renderer.h`** (public):
  - `CreateMesh`, `LoadTexture("textures/crate.png")` and
    `CreateMaterial({ .Texture = ..., .Color = ... })` hand out resources as `std::shared_ptr`.
  - `Submit(mesh, material, transform)` queues a draw for the frame being built.
  - Games get the renderer from `Application::GetRenderer()`.
- **`Viva/MeshData.h`** and **`Viva/Primitives.h`** (public): `Vertex` and `MeshData`, now usable by
  games, and built-in `Primitives::Cube()` and `Primitives::Plane(size, repeats)`.
- **`sandbox/src/DemoScene.h/.cpp`**: the scene from M6–M7, built by the game. It recolors the
  built-in cube for the pillars.
- **Deferred deletion:** when the game drops the last reference to a resource, the renderer
  destroys it only once the GPU can't be using it any more.
- **Materials** (texture + color, Unlit shader):
  - Each owns a descriptor set (set 1) from the new growable **`DescriptorAllocator`**.
  - A material without a texture uses a built-in **white** one.
  - `LoadTexture` returns the same texture when a name is loaded twice.
- **Shared pipeline layout:** one `VkPipelineLayout`, owned by the renderer, used by every pipeline.
- **Draw list:** `EndFrame` sorts the frame's submissions by shader, material and mesh, and binds
  only what changes. The material color reaches the shader as a push constant, next to the model
  matrix.
- **The frame is split** into `BeginFrame` (wait for the GPU, acquire an image) and `EndFrame`
  (record, submit, present). The main loop now calls `BeginFrame` *before* reading input, which
  shortens the input latency (deferred from M3).

## Concepts

### From hardcoded draws to an API

Until M7 the renderer itself held the demo meshes and decided what to draw. A game engine works
the other way round. The game owns its content, and each frame tells the renderer what to draw
and where. That's Unity's `Graphics.DrawMesh(mesh, matrix, material)`:

```cpp
// OnStart (DemoScene::Load):
m_CubeMesh = renderer.CreateMesh(Primitives::Cube());
m_CrateMaterial = renderer.CreateMaterial({ .Texture = renderer.LoadTexture("textures/crate.png") });
// OnUpdate (DemoScene::Draw), every frame:
renderer.Submit(m_CubeMesh, m_CrateMaterial, SpinningCubeTransform(seconds));
```

Submissions last one frame, so the game submits everything it wants drawn every frame, from
`OnUpdate`. That's the only time a frame is being built. A `Submit` from anywhere else stops the
Debug build with an assert. M10's `MeshRenderer` component will submit automatically for every
object in the scene.

Creating a mesh or texture copies data to the GPU and **waits** for it, so do it while loading
(`OnStart`) and reuse the result.

### Pimpl: keeping Vulkan out of the public header

A C++ header shows a class's private members too, so a `Renderer` with Vulkan members would pull
Vulkan into every game file that includes it. The fix is the **pimpl** idiom ("pointer to
implementation"):
- The public class has one private member, `std::unique_ptr<Impl> m_Impl`.
- `struct Impl` is only *declared* in the header, and *defined* in `Renderer.cpp`, with all the
  Vulkan state and logic. `Renderer`'s public functions just forward to it.
- Games see the API and nothing else. Changing the renderer's internals doesn't even recompile
  them.

C# never needs this, since assemblies expose only what you mark public. In C++, the header *is*
the interface, private parts included.

The same trick hides the resources. The header only declares `class Mesh;` and so on, and the
game holds `std::shared_ptr<Mesh>` without knowing what's inside, like an opaque handle.

### Resources as shared pointers

`std::shared_ptr` is reference counting: copies share one object, and the last one to go away
destroys it. It's the closest C++ gets to C#'s object references, which keep an object alive while
anything refers to it. A material holds `shared_ptr`s to its shader and texture, so a texture used
by three materials lives as long as any of them. Unity makes you call `Destroy()` on assets
explicitly; here, dropping the last reference is enough.

`LoadTexture` also keeps a `std::weak_ptr` per name, C#'s `WeakReference`: it remembers a texture
without keeping it alive. Loading the same name while the texture is still in use returns it
instead of loading a copy, like Unity's `Resources.Load`.

### Deferred deletion

With two frames in flight (M3), dropping the last reference to a texture doesn't mean the GPU is
done with it. A frame already submitted may still be drawing with it. Destroying it then would
corrupt that frame, or crash.

So the `shared_ptr`s the renderer hands out carry a custom **deleter** (`Impl::Track` in
`Renderer.cpp`):
1. When the last reference goes, the deleter doesn't delete. It parks the resource in a
   **release list** (`FrameData::ReleasedResources`), the one of the newest frame that may still
   draw with it: the frame being built, or the one just submitted.
2. The next time that frame slot comes around, `BeginFrame` waits for its fence. The GPU finishes
   frames in order, so after that wait nothing can be using what's in the list, and the list is
   destroyed.
3. At shutdown, the renderer waits for the GPU to go idle, then destroys released resources
   immediately.
4. It then checks that the game released everything. A resource kept past that point (in a global
   variable, say) would be released after the renderer is gone: that's logged as an error in every
   build.

The release list holds every kind of resource as `std::unique_ptr<GpuResource>`. `GpuResource` is
a base class with a **virtual destructor**, so destroying a `Mesh` through a `GpuResource` pointer
runs `Mesh`'s destructor. In C# terms, it's a list of `IDisposable`.

**Destroying one resource can release others:** a material holds its texture. `DestroyReleased`
takes the list out (`std::exchange`) before destroying it, so anything released meanwhile lands
safely in a list for later.

**Destruction order:** the renderer is now destroyed in `~Application`, after the game's own
members. A game's `shared_ptr` members are therefore released before the renderer checks.

### Materials and the shared pipeline layout

The engine's types map onto Unity's:

| VivaEngine | Unity |
|---|---|
| `Material`: texture + color, drawn with the Unlit shader | Material |
| `Mesh` | Mesh |
| `Texture` | Texture2D |
| `Shader` (internal for now): vertex + fragment shader built into a pipeline | Shader (one pass) |

Every pipeline uses one **pipeline layout**, created once by the renderer:
- set 0: the camera;
- set 1: the material's texture;
- push constants: the model matrix and the material color, 80 bytes.

Bound descriptor sets stay valid as long as the pipeline layout matches. So the camera's set is
bound once per frame, before any pipeline, and stays bound through every draw.

Only one shader exists so far, so `Shader` is internal and every material uses Unlit. Letting
games load their own shaders is a small step once something needs one.

### A growable descriptor allocator

A descriptor pool has a fixed capacity, set when it's created. `DescriptorAllocator` keeps a list
of pools and opens a new one when the others are full. Its pools are created with
`FREE_DESCRIPTOR_SET_BIT`, so a destroyed material can give its set back individually. The camera
sets come from it too, and live as long as the renderer.

### Sorting draws

Each change of pipeline, descriptor set or vertex buffer costs the GPU and driver some work. So
`RecordDraws`:
1. sorts the frame's submissions by shader, then material, then mesh;
2. binds each only when it changes;
3. pushes each draw's model matrix and color, and draws.

The demo scene's 10 draws need 1 pipeline bind, 3 material binds and 3 mesh binds. The order
doesn't change the picture, because the depth buffer decides what's in front (transparent
objects, later, would need back-to-front order).

### Input latency: BeginFrame before input

With vsync, the CPU spends most of each frame waiting. Timing the calls shows where: about 16 ms
(one refresh at 60 Hz) in `vkWaitForFences`, the wait for the frame two frames back. The acquire
takes 0.04 ms and the present 0.15 ms.

- **Until M7**, each loop iteration read input, updated, and *then* reached that wait inside
  `DrawFrame`. The input a frame was drawn with was already a refresh old.
- **Now** the loop starts with `BeginFrame` (the fence wait and the acquire), then reads input,
  then updates. The input is as fresh as it can be when the frame is drawn, a whole refresh newer
  than before.

Two details keep this correct:
- Once `BeginFrame` succeeds, `EndFrame` must follow, even if the game quits that frame, because
  it submits the work that signals the frame's fence.
- Input flags ("pressed this frame") are now cleared right after the game's update, not before
  reading events. A key press that arrives during a pass that can't draw (the swapchain being
  rebuilt) waits for the next update instead of being lost.

## Reading guide

1. **`sandbox/src/DemoScene.cpp`**: the game's side. `Load()` creates meshes and materials,
   `Draw()` submits them; `ColoredCube()` edits a built-in mesh's vertex colors.
2. **`engine/include/Viva/Renderer.h`**, then **`MeshData.h`** and **`Primitives.h`**: the
   public API, `MaterialSettings`' defaults, and the pimpl `Impl`.
3. **`engine/src/Core/Application.cpp`**: the loop's new order (`BeginFrame`, events, updates,
   `EndFrame`, clearing input), and the comment on `~Application`.
4. **`engine/src/Renderer/Renderer.cpp`**, from the top:
   - `ObjectPushConstants`, `DrawCommand` and `struct Renderer::Impl` with `Track`;
   - the one-line public functions;
   - `~Impl` (shutdown) and `Initialize` (with the shared pipeline layout);
   - the resource functions (`LoadTexture`'s cache);
   - `BeginFrame`, `EndFrame`, `RecordDraws`.
5. **`engine/src/Renderer/GpuResource.h`** and **`FrameResources.h`**: the virtual destructor and
   the per-frame `ReleasedResources`.
6. **`engine/src/Renderer/Material.h/.cpp`**, **`DescriptorAllocator.h/.cpp`** and
   **`Shader.h/.cpp`**. Also `Pipeline.h`, whose `Layout` is now borrowed.
7. **`engine/src/Core/Primitives.cpp`**: the cube and plane, moved here from M7's renderer.
8. **`shaders/Unlit.vert`**: the `Color` push constant tinting the vertex color.

## How to test

1. **Run** the Sandbox. You see the same scene as in M7, except that the cubes' faces (crate and
   pillars) are now evenly lit. The subtle gradient across them was a trick in M7's renderer-side
   cube, and the built-in `Primitives::Cube()` has plain white vertices.
2. **Fly around**, resize, minimize and restore: everything works as before, and validation stays
   silent.
3. **Esc:** the process exits with code 0, and no "outlived the renderer" error appears in the log.
4. **RenderDoc:** in the Event Browser, one `vkCmdBindPipeline`, then three groups of draws (the
   floor, the 8 pillars, the crate), each with one descriptor-set bind and one vertex/index bind.
5. **Experiments** (rebuild after each, and revert afterwards):
   - In `DemoScene::Load`, give the pillars a color: `CreateMaterial({ .Color = { 1.0f, 0.6f,
     0.6f, 1.0f } })`. The material color tints the vertex colors.
   - In `DemoScene::Draw`, submit the crate a second time with
     `glm::translate(glm::mat4(1.0f), { 3.0f, 1.0f, 0.0f })`. A second crate appears, sharing the
     mesh and material.
   - **Stress deferred deletion:** in `Main.cpp`'s `OnUpdate`, create a new mesh and material
     every frame, keep them in members, and submit them. Each frame then releases the previous
     frame's pair while the GPU may still be drawing it. Validation stays silent, and memory
     doesn't grow. But the frame rate halves: each upload waits for the GPU, including the frame
     in flight. That's why creating resources belongs in loading code.
   - **Keep a resource past shutdown:** copy `m_CrateMaterial` into a `static
     std::shared_ptr<Viva::Material>`. At exit, the log shows "1 GPU resource(s) outlived the
     renderer", and the Debug build stops there.
   - Call `GetRenderer().Submit(...)` from `OnStart`. The Debug build stops: no frame is being
     built yet.

## Known limitations

- **One shader:** materials can't choose another yet, and all of them share one layout (one
  texture, one color).
- **No instancing:** every submission is its own draw call. Many copies of one mesh would be better
  drawn in one instanced call.
- **Uploads block:** creating a mesh or texture waits for the GPU (see the stress experiment).
  Batching uploads, or recording them into the frame's own command buffer, is the fix when a game
  needs to create things while running.
- **The camera** still belongs to `Application`. M10 makes it a component in the scene.
