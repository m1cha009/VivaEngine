# M3: Swapchain and clear screen (first pixels)

## What was built

The engine draws. Every frame it clears the window to a color that slowly cycles through the
hues, through the full Vulkan frame loop. That loop is the same one every later milestone draws
into.

- **`Swapchain`** (`engine/src/Renderer/Swapchain.h/.cpp`):
  - the set of images the window shows in turn, plus an image view for each;
  - it picks an sRGB surface format and the present mode (FIFO when `VSync` is on, MAILBOX when
    off), and sizes itself in pixels.
- **`FrameResources`**: two **frames in flight**, each with its own command pool and buffer, an
  "image acquired" semaphore and an "in flight" fence. There's also one "render finished"
  semaphore per swapchain image.
- **`Renderer::DrawFrame()`**, the frame loop:
  1. wait;
  2. acquire;
  3. record (barrier, dynamic-rendering clear, barrier);
  4. submit;
  5. present.
  
  It rebuilds the swapchain when the window's pixel size changes or Vulkan reports it out of date,
  and skips frames with no area.
- **Synchronization validation** is now enabled in Debug builds (through `VK_EXT_layer_settings`),
  so mistakes in barriers and semaphores show up as validation errors too.
- **`ApplicationSettings::VSync`** and the sandbox flag `--no-vsync`.

The log now includes:

```
[   0.172] [Info ] Vulkan validation layer enabled, with synchronization validation
[   0.570] [Info ] Swapchain: 1280x720 pixels, 3 images, VK_FORMAT_B8G8R8A8_SRGB, VK_PRESENT_MODE_FIFO_KHR
```

The `Swapchain:` line appears again for every rebuild (resize). The title bar shows the display's
refresh rate (about 60 FPS here), and CPU use dropped from a full core to a fraction of one.

## Concepts

### The swapchain

A window can't be drawn into directly. Vulkan gives you a **swapchain**: a small queue of images
(three here). The display shows one image while you draw into another. When you're done, you
**present** the image (hand it to the display), and next frame you **acquire** the next free one.
Unity does exactly this behind the scenes. The "back buffer" you never see is a swapchain image.

Creating one means choosing:
- **The format.** `VK_FORMAT_B8G8R8A8_SRGB`: 8 bits per channel, stored in sRGB. Our colors are
  linear, and the GPU converts them to sRGB when writing, which is what monitors expect. It's the
  same idea as Unity's *Linear* color space. A side effect: a value of 0.5 looks brighter than
  "half gray", which is why the cycling colors look pastel.
- **The present mode**:
  - **FIFO**: images queue up and the display takes one per refresh. This is vsync. Always
    available, and the frame rate equals the refresh rate.
  - **MAILBOX**: a newer image replaces a waiting one. No tearing and low latency, but the GPU
    renders flat out (`--no-vsync`).
  - **IMMEDIATE**: shows images at once, with tearing.
- **The size**, in pixels. On a Retina Mac that's twice the window's size in points.

A swapchain has a fixed size, so **resizing the window means building a new one**. The renderer
compares the window's pixel size with the size of the last build. It also rebuilds when Vulkan
answers `VK_ERROR_OUT_OF_DATE_KHR` or `VK_SUBOPTIMAL_KHR`, its way of saying "this swapchain no
longer fits the window".

Swapchain images belong to the swapchain, but to render into one you need an **image view**: a
description of how to look at the image (format, which mip levels and layers). Textures in M7 get
views too.

### Command buffers: recording work for the GPU

The CPU doesn't draw. It **records commands** into a **command buffer** ("clear this image",
"draw these triangles"), then **submits** the buffer to a queue, and the GPU runs it later on its
own. Command buffers get their memory from a **command pool**. Resetting the pool resets every
buffer in it, which is how each frame starts from a clean slate.

### Synchronization: the hard part

The CPU and the GPU run **in parallel**, and the GPU runs commands in parallel too. Nothing waits
for anything unless you say so. Vulkan has three tools for saying so:

| Tool | Who waits for whom | Used here for |
|---|---|---|
| **Fence** | The CPU waits for the GPU | "Has the GPU finished frame N−2, so I can reuse its command buffer?" |
| **Semaphore** | The GPU waits for the GPU (or presentation) | "Don't draw into the image before it's acquired", "don't present it before it's drawn" |
| **Pipeline barrier** | Work inside a command buffer waits for earlier work | "Finish writing the image before presentation reads it", plus layout changes |

In **synchronization2** (Vulkan 1.3), a barrier names its **stages** (*where* in the GPU's
pipeline, such as color output) and **access types** (*what kind* of memory access, such as
color writes). Our clear needs two image barriers per frame:

1. **UNDEFINED → COLOR_ATTACHMENT_OPTIMAL**, so the image can be drawn into. "Undefined" means
   "throw the old contents away", which is fine because we clear it anyway.
2. **COLOR_ATTACHMENT_OPTIMAL → PRESENT_SRC_KHR**, so the display can read it.

Those **layouts** exist because GPUs store an image differently depending on its job (drawn
into, shown on screen, sampled as a texture). Vulkan makes you announce each change of job.

### Frames in flight

If the CPU waited for the GPU to finish every frame before starting the next, both would spend
half their time idle. With **two frames in flight**, the CPU records frame N+1 while the GPU
still renders frame N. Each frame slot has its own command buffer, semaphore and fence, so the
slots never step on each other. The fence at the top of `DrawFrame` makes the CPU wait only if
it gets two frames ahead. More slots would add input latency for little gain.

The "render finished" semaphores are the exception: there's **one per swapchain image**, not
per frame. Presentation may still be waiting on an image's semaphore when the same frame slot
comes around again, and reusing it then is a bug (the validation layer reports it).

### Dynamic rendering

Classic Vulkan needs a `VkRenderPass` and a `VkFramebuffer` declared up front, before you can draw
anything. **Dynamic rendering** (Vulkan 1.3, enabled in M2) skips both:
`vkCmdBeginRendering` takes the image views to draw into directly, with what to do at the start
(`loadOp = CLEAR`: fill with the clear color) and at the end (`storeOp = STORE`: keep the
result). That pair, `vkCmdBeginRendering` and `vkCmdEndRendering`, is where M4's draw calls will
go.

### The frame, step by step (`Renderer::DrawFrame`)

1. **Wait** on this slot's fence until the GPU has finished the frame that used it last. Only
   then reset the fence. Resetting it before an early `return` would leave it unsignaled forever.
2. **Acquire** the next swapchain image. The call returns the image's index at once; the "image
   acquired" semaphore gets signaled once the image is really free.
3. **Record**: barrier, dynamic-rendering clear, barrier.
4. **Submit** with `vkQueueSubmit2`:
   - wait for "image acquired" before the color-output stage;
   - signal "render finished" when done;
   - signal the fence.
5. **Present**, waiting for "render finished". With FIFO, this is where the loop gets tied to the
   display's refresh rate, which is why the CPU now rests between frames.

### Resizing and minimizing

The loop still skips whole frames, and sleeps, while the window is minimized (M1). It does the
same when the window has no drawable area without being minimized: Windows lets you drag a
window down to zero height. The renderer also skips any frame with no area, and `Swapchain::Create`
refuses to build a 0×0 swapchain. There's a race
here, and the validation layer caught it during testing: Windows reports the surface as 0×0 a
moment *before* SDL flags the window as minimized. A rebuild in that gap now just waits for a
later frame.

Rebuilding uses `vkDeviceWaitIdle`, which waits until the GPU has nothing left to do. Then nothing
can still be using the old swapchain. It's a blunt tool, but resizing is rare.

## Reading guide

1. **`engine/src/Renderer/FrameResources.h`**: what one frame in flight needs, and why "render
   finished" is per image. Then `FrameResources.cpp`: the fence created already signaled.
2. **`engine/src/Renderer/Swapchain.h`** and **`Swapchain.cpp`**:
   - `ChooseSurfaceFormat` and `ChoosePresentMode`, with the three present modes explained;
   - `Create()`: the extent rules, the 0×0 case, the image count, `oldSwapchain`, the image views.
3. **`engine/src/Renderer/Renderer.h`**: the members in creation order (and so destruction order),
   and `m_Window` as a reference member.
4. **`engine/src/Renderer/Renderer.cpp`**:
   - **`DrawFrame()`**, step by step against [the list above](#the-frame-step-by-step-rendererdrawframe);
   - **`TransitionImage()`**: the stages, access masks and layouts of each barrier;
   - **`RecreateSwapchain()`** and **`~Renderer()`**, which both wait for the GPU to go idle.
5. **`engine/src/Renderer/VulkanContext.cpp`** (`CreateInstance`): the layer settings for
   synchronization validation, chained in front of the messenger settings.
6. **`engine/src/Core/Application.cpp`**: `DrawFrame()` at the end of each frame, after `OnUpdate`.

## How to test

1. **Run** the Sandbox (`windows-debug`). The window slowly cycles through colors. The title shows
   your monitor's refresh rate (60, 144, …), and Task Manager shows low CPU use.
2. **Resize** quickly, make the window tiny, **minimize**, restore, **maximize**. The colors keep
   cycling, and there's no `[Warn]` or `[Error]` in the log.
3. **`--no-vsync`** (add it to the run configuration's program arguments): the log says
   `VK_PRESENT_MODE_MAILBOX_KHR` and the FPS shoots up.
4. **RenderDoc**: launch `Sandbox.exe` from RenderDoc (*Launch Application*) and capture a frame
   with F12. In the event browser you'll see the frame exactly as recorded: two barriers and
   `vkCmdBeginRendering`/`vkCmdEndRendering`. Click the image to see the clear color.
5. **Experiments** (revert afterwards):
   - In `TransitionImage`'s second call, change `VK_IMAGE_LAYOUT_PRESENT_SRC_KHR` to
     `VK_IMAGE_LAYOUT_GENERAL`. The validation layer complains that presented images must be in
     `PRESENT_SRC_KHR`.
   - Change `FrameResources::kFramesInFlight` to 1. It still works, but the CPU now waits for
     the GPU every frame.
   - Move `vkResetFences` above `vkAcquireNextImageKHR`, then resize. Eventually a frame
     returns early with the fence reset, and the next wait hangs forever. That's why it sits
     where it does.

## Known limitations

- **Windows pauses the loop while you drag a window edge.** The OS runs its own modal loop during
  the drag, so the content doesn't follow live, and the swapchain is rebuilt when you let go.
- **Swapchain rebuilds wait for the GPU to go idle** (`vkDeviceWaitIdle`). It's simple and safe,
  but causes a short hitch, which is fine for a resize.
- **Clearing only**: no geometry yet. M4 draws the first triangle.

## Verified on

- **Windows 11 Pro** (RTX 3080 Ti), Debug and Release, zero warnings. An automated script tested:
  - **Validation:** with synchronization validation on, it reported nothing across 13 swapchain
    rebuilds from rapid resizes (down to 140×40), three minimize/restore cycles, maximizing to
    2560×1369, and Esc/close.
  - **The 0×0 race** described above was found by the validation layer, fixed, and re-tested.
  - **A zero-height window** (dragged down to nothing, not minimized) uses 0 ms of CPU.
  - **Screenshots:** they showed the cycling clear color, including the maximized size.
  - **Frame rate and CPU:** FIFO ran at about 57–60 FPS (the display's rate) with low CPU use,
    `--no-vsync` used MAILBOX, and CPU use while minimized was 0 ms.
- **CI (macOS):** M2's run found the GitHub runner's *Apple Paravirtual device* through MoltenVK
  1.4.2, so CI now runs the real frame loop on a Mac. See
