# M2: Vulkan instance, validation and device

## What was built

The engine now talks to the GPU through Vulkan. Nothing is drawn yet (that's M3), but every
Vulkan object that drawing builds on exists, and the validation layer watches every Vulkan call
in Debug builds.

- **`VulkanContext`** (`engine/src/Renderer/`) creates, in order:
  1. the **instance**: Vulkan 1.3, the surface extensions SDL asks for, and portability
     enumeration for macOS;
  2. in Debug builds, the **validation layer** and a **debug messenger** that sends its messages
     to `Log`;
  3. the **surface** for our window;
  4. the **physical device**: it lists every GPU, logs why any is unsuitable, and picks the best;
  5. the **logical device**, with the swapchain extension and the Vulkan 1.3 features
     *dynamic rendering* and *synchronization2* turned on;
  6. the **graphics and present queues**.

  It destroys them in reverse order.
- **`VK_CHECK(call)`** reports any failed Vulkan call with its `VkResult` name, file and line, and
  stops the program, in every build.
- **`Renderer`**, a small front class with no Vulkan in its header. `Application` owns it, so
  Core code still never sees `vulkan.h`.
- **`Window`** gained `GetRequiredVulkanExtensions()` and `CreateVulkanSurface()`.

A Debug run on the dev PC now starts like this:


## Concepts

### Why Vulkan feels like so much work

Unity hides the graphics API completely: its render pipeline talks to Direct3D, Metal or Vulkan
for you. Older APIs like OpenGL and Direct3D 11 also hide a lot: the driver guesses what you
want, manages memory and inserts synchronization behind your back. Vulkan is **explicit**. You
create every object yourself, say exactly which features you'll use, and later (M3) decide when
the GPU may start and finish each piece of work.

That's more code, but nothing is hidden. Performance is predictable, and you see exactly what a
renderer does, which is the point of this project.

### The loader, drivers and layers

When the engine calls a Vulkan function, the call goes through three parts:

```
Engine  ──►  Vulkan loader (vulkan-1.dll)  ──►  layers (optional)  ──►  driver (ICD)  ──►  GPU
```

- **The loader** is the DLL we link against. It finds the installed drivers and layers through
  small JSON files (registered in the Windows registry, or in `/usr/local/share/vulkan` on macOS).
- **The driver** (an "ICD", installable client driver) is the GPU vendor's implementation:
  NVIDIA's on this PC. On macOS it's MoltenVK or KosmicKrisp, which translate Vulkan to Metal.
- **Layers** sit between the loader and the driver and can watch or change calls. We enable one,
  the **validation layer**. Other programs install "implicit" layers that load into every Vulkan
  app: on this PC, Steam's overlay, RTSS (MSI Afterburner) and Overwolf.

Overwolf's layers were built for Vulkan 1.2, and the loader warns about that because we ask for
1.3. That warning describes this PC's software, not our code, so the engine logs loader messages
as **Info** with a `[Vulkan loader]` prefix. Messages from the validation layer, which *are* about
our code, keep their Warning or Error level.

### The instance

`VkInstance` is the engine's connection to Vulkan as a whole. Creating it declares:
- **the Vulkan version** we're written for (1.3);
- **instance extensions**, extra abilities beyond core Vulkan. Window surfaces are an extension,
  because Vulkan itself doesn't know about windows: `VK_KHR_surface`, plus the per-OS one SDL
  asks for, such as `VK_KHR_win32_surface`;
- **layers**, such as validation.

On macOS, drivers that translate to Metal are "portability" drivers. The loader only lists them if
the app enables `VK_KHR_portability_enumeration` and sets a matching flag. The engine does that
whenever the extension exists, which is harmless on Windows.

### Validation: the console errors of graphics programming

Vulkan drivers check almost nothing; a wrong call is undefined behavior, and might work on one GPU
and crash on another. The **validation layer** checks every call against the specification and
reports mistakes, like the warnings Unity shows in its console. It's slow, so only Debug builds
enable it.

Messages arrive in `DebugCallback` (`VulkanContext.cpp`) through a **debug messenger**:
- Each message names the rule it broke, with a link to the specification, for example
  `VUID-vkDestroyInstance-instance-00629`.
- The same messenger settings are also passed to `vkCreateInstance` itself, so mistakes during
  instance creation and destruction get reported too, when the real messenger doesn't exist.

### The surface

A `VkSurfaceKHR` is the window, as seen by Vulkan: something images can be shown on. Creating it
is OS-specific, so SDL does it (`SDL_Vulkan_CreateSurface`). That needs SDL, which lives only in
`Platform/`, *and* Vulkan's types, which live only in `Renderer/`. The solution is that `Window.h`
**declares** the two handle types it needs: `struct VkInstance_T; struct VkSurfaceKHR_T;`. On
64-bit systems, `vulkan.h` defines `VkInstance` as `VkInstance_T*` and `VkSurfaceKHR` as
`VkSurfaceKHR_T*`, so the renderer can pass its handles straight in, and neither folder includes
the other's library.

### Physical device, logical device, queues

- A **physical device** (`VkPhysicalDevice`) is a GPU as Vulkan sees it. It isn't created, only
  *chosen* from a list. A laptop often has two: integrated and discrete. The engine rejects GPUs
  that lack Vulkan 1.3, the swapchain extension, the two features below, or a queue that can draw
  and present to our surface. Among the rest it prefers a discrete GPU.
- A **logical device** (`VkDevice`) is our own connection to that GPU, created with exactly the
  extensions and features we'll use. Almost every later Vulkan object is created from it.
- **Queues** are where work is submitted to the GPU. They come in **families** with different
  abilities: graphics, compute, transfer, and present (showing images on a surface). We need a
  graphics queue and a present queue; on desktop GPUs one family usually does both.

### Features, and pNext chains

Two Vulkan 1.3 features are switched on now for M3:
- **Dynamic rendering** lets you start drawing into images directly
  (`vkCmdBeginRendering`), instead of declaring `VkRenderPass` and `VkFramebuffer` objects up
  front. It's simpler, and what modern Vulkan code and vkguide use.
- **Synchronization2** is a cleaner version of Vulkan's barriers and queue submission, which
  control when the GPU may read and write each image.

Every Vulkan 1.3 GPU supports both, but features must still be enabled explicitly. They're passed
through a **pNext chain**. Vulkan extends its structs by linking extra structs through their
`pNext` pointer, with each struct's `sType` saying what it is:

```cpp
VkPhysicalDeviceVulkan13Features features13 { .sType = ..._VULKAN_1_3_FEATURES, .synchronization2 = VK_TRUE, .dynamicRendering = VK_TRUE };
VkPhysicalDeviceFeatures2 features { .sType = ..._FEATURES_2, .pNext = &features13 };
VkDeviceCreateInfo createInfo { .sType = ..._DEVICE_CREATE_INFO, .pNext = &features, ... };
```

The same pattern fetches the driver's name and version (`VkPhysicalDeviceVulkan12Properties`).

### Designated initializers

```cpp
const VkApplicationInfo appInfo {
    .sType = VK_STRUCTURE_TYPE_APPLICATION_INFO,
    .pEngineName = "VivaEngine",
    .apiVersion = VK_API_VERSION_1_3,
};
```

This is C++20's version of a C# object initializer. Fields are named, and every field that isn't
mentioned is zero, which for Vulkan structs means "not used". The fields must appear in the order
they're declared in the struct. Clang warns about every field left out, so our Clang flags turn
that one warning off (`cmake/CompilerWarnings.cmake`).

### Extension functions are looked up by name

The loader exports core functions like `vkCreateInstance` directly. Extension functions, like
`vkCreateDebugUtilsMessengerEXT`, must be fetched at runtime with `vkGetInstanceProcAddr` and cast
to the right function-pointer type. **`reinterpret_cast`** is C++'s "trust me" cast between
unrelated pointer types. It's only used where an API demands it, as here.

### Errors without exceptions

There are two kinds of failure:
- **Expected on a healthy machine**: no GPU supports Vulkan 1.3, or instance or device creation
  fails. These are checked explicitly, logged in plain words, and reported upward:
  `VulkanContext::Create` returns `nullptr`, `Renderer::Create` returns `nullptr`, and `Run()`
  returns `EXIT_FAILURE`.
- **Signs of a bug or a broken system** (out of memory, a lost device) go through **`VK_CHECK`**,
  which logs the call and its `VkResult` name, then stops the program. Under a debugger it breaks
  at the spot. Carrying on would only crash somewhere else later, far from the real cause.

### Destruction order and RAII

Every Vulkan object depends on the ones created before it, so `~VulkanContext()` destroys them in
**reverse order**: device, surface, messenger, instance. The same rule holds one level up.
`Application` destroys the renderer before the window, because the surface belongs to the window;
it does that with explicit `reset()` calls and by declaring `m_Renderer` after `m_Window` (C++
destroys members in reverse order of declaration).

`VulkanContext::Create` builds step by step. If a step fails, it just returns `nullptr`, and the
half-built context's destructor cleans up whatever exists. That's why every destructor line
checks its handle first.

## Reading guide

1. **`engine/src/Renderer/Renderer.h`** and **`Renderer.cpp`**: the front. Notice:
   - `class VulkanContext;` (a declaration only), which is why the header needs no `vulkan.h`;
   - `std::move` handing the `unique_ptr` over.
2. **`engine/src/Renderer/VulkanContext.h`**: the member list *is* the list of objects above.
   Notice `kApiVersion` and the private steps of `Create()`.
3. **`engine/src/Renderer/VulkanContext.cpp`**, in this order:
   - **`Create()`**: instance (with its messenger), then surface, then `PickPhysicalDevice()`,
     then `CreateDevice()`.
   - **`CreateInstance()`**: the extension and layer lists, the portability flag, the
     designated initializers, and the messenger settings in `pNext`.
   - **`PickPhysicalDevice()`** and **`CheckDevice()`**: every requirement a GPU must meet, one
     line each. Notice the queue family search and the features query (the first pNext chain).
   - **`DebugCallback()`** and **`DebugMessengerInfo()`**.
   - **`CreateDevice()`**: one queue per family (the `std::set`), the features chain, and the
     driver-info chain.
   - **`~VulkanContext()`**: reverse order.
4. **`engine/src/Renderer/VulkanCheck.h`** and **`VulkanCheck.cpp`**: the macro and
   `string_VkResult`.
5. **`engine/src/Platform/Window.h`** and **`Window.cpp`**: `GetRequiredVulkanExtensions()` and
   `CreateVulkanSurface()`, and how they use Vulkan's types without `vulkan.h`.
6. **`engine/src/Core/Application.cpp`**: the renderer is created after the window, and reset
   before it.
7. **`cmake/CompilerWarnings.cmake`**: the Clang-only flag for designated initializers.

## How to test

1. **Run** the Sandbox (`windows-debug`). Check the log for the lines shown above:
   - *Vulkan validation layer enabled*;
   - the GPU list;
   - *Using NVIDIA GeForce RTX 3080 Ti …*.
   
   There must be no `[Warn]` or `[Error]` lines. The `[Vulkan loader]` Overwolf lines are
   expected on this PC.
2. **Resize, minimize, maximize** and close the window. Still no validation output.
3. **Release** (`windows-release`): no validation line, and the same GPU lines.
4. **Experiments** (revert afterwards):
   - In `~VulkanContext()`, comment out the `vkDestroySurfaceKHR` line. At shutdown the
     validation layer reports `vkDestroyInstance(): … has 1 leaked objects … VkSurfaceKHR`.
   - Set a breakpoint inside `DebugCallback` and repeat the leak: the call stack shows exactly
     which Vulkan call triggered the message.
   - In CLion's run configuration, add the environment variable `VK_LOADER_DEBUG=all` (in
     the *Environment variables* field) and run. The loader prints how it finds the driver and
     every layer. It's long, but it shows the loader at work.
5. **RenderDoc** can launch the Sandbox now, but there's nothing to capture until M3 draws
   frames.

## Known limitations

- **GPU choice** is automatic (discrete over integrated), with no setting to override it.
- **The messenger** only forwards warnings and errors; info and verbose messages are skipped.
- **No GPU memory management yet**: buffers and images arrive in M5 (VMA) and M6.
- **Loader warnings** are logged as Info. A broken driver install would still show as an
  error, because the loader reports those at Error severity.
- **CI:** whether GitHub's virtual Mac exposes a Vulkan 1.3 GPU is unknown until the first M2
  run. CI's new *Show Vulkan devices* step records what it finds.

## Verified on

- **Windows 11 Pro** with an RTX 3080 Ti (driver 616.64), Debug and Release, zero warnings.
  - **Validation was silent** through startup, two resizes, minimize, restore, maximize, Esc and
    the close button. Both exits had code 0 and nothing on stderr.
  - **A deliberately leaked surface** was reported as a validation error at shutdown, which
    proves the debug messenger works, including during instance destruction.
  - **Release** runs without the validation layer.
- **macOS**: see the new M2 items in [`docs/MacChecklist.md`](../MacChecklist.md).
