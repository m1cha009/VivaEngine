# M0: Project skeleton

## What was built

The foundation for every later milestone. There's no window yet: the program starts, prints
some version numbers and exits. M0 sets up the build, the dependencies, the folder rules and the
first engine code, which is logging and asserts.

- **Two CMake targets.** `VivaEngine` is the engine, a static library. `Sandbox` is an
  executable that uses it the way a game would.
- **Four presets**: `windows-debug`, `windows-release`, `macos-debug` and `macos-release`. CLion
  and the command line both use them.
- **Dependencies.** CMake downloads SDL3 3.4.18 (built as a static library) and GLM 1.0.3. Vulkan
  1.4.363 comes from the installed LunarG SDK.
- **Engine code:**
  - `Viva::Log`, for logging.
  - `VIVA_ASSERT`, for asserts.
  - Functions that report the versions of the engine and its libraries.
  - `BreakIntoDebuggerOrExit()`, the first platform-specific function.
- **Shader compilation.** The CMake function `viva_compile_shaders()` turns GLSL files into SPIR-V
  during the build. Nothing uses it yet; the first shaders arrive in M4.
- **`scripts/build.cmd`**, for building from a plain Windows shell.

The Debug sandbox prints:

```
[   0.000] [Info ] VivaEngine 0.1.0
[   0.000] [Info ] SDL 3.4.18
[   0.000] [Info ] Vulkan headers 1.4.363
[   0.005] [Info ] Vulkan loader 1.4.363
[   0.005] [Info ] GLM 1.0.3
[   0.005] [Trace] Trace messages like this one only appear in Debug builds
```

## Concepts

### How a C++ program gets built

In C#, you hand the compiler a whole project and it produces one assembly, where every class can
see every other class. C++ works one file at a time, in three steps:

1. **Preprocessor.** Handles the lines that start with `#`. `#include "Viva/Log.h"` pastes the
   contents of that file in place, literally. `#define` creates text-replacement macros. `#if`
   keeps or drops code before the compiler ever sees it.
2. **Compiler.** Compiles each `.cpp` file, together with everything it included, into an
   **object file** (`.obj` on Windows, `.o` on macOS). One `.cpp` plus its includes is called a
   **translation unit**. While compiling `Main.cpp`, the compiler knows nothing about `Log.cpp`.
3. **Linker.** Combines all object files and libraries into the `.exe`, and connects every
   function call to the compiled code of that function.

This is why C++ has **headers**. To call a function, a `.cpp` file only needs its
**declaration**: name, parameters and return type. The **definition**, meaning the body, can live
in any other `.cpp`. For example, `GetSDLVersion()` is *declared* in `Viva/Version.h`, which
`Main.cpp` includes and calls. It's *defined* in `src/Platform/SDLVersion.cpp`. The linker joins
the two. C# has nothing like this, because its compiler sees all files at once.

`#pragma once` at the top of a header means "paste me only once per translation unit", even when
several includes lead to the same header.

Two kinds of errors follow from this. A **compile error** means one file is wrong on its own:
bad syntax, an unknown name or mismatched types. A **link error** (`unresolved external symbol`
on MSVC, `undefined symbol` on Clang) means some code called a function that was declared but
never defined anywhere.

### CMake, targets and presets

**CMake** doesn't compile anything. It reads the `CMakeLists.txt` files and **generates** a build
system. We use **Ninja**, a small and fast build tool, and Ninja runs the compiler and linker.
When a `CMakeLists.txt` changes, CMake re-runs automatically.

A **target** is something to build (a library or an executable) together with its **usage
requirements**: the include folders, defines and libraries that anyone using it needs. That's
the closest thing to a Unity **assembly definition (asmdef)**. `VivaEngine` plays the role of an
engine asmdef, and `Sandbox` the game assembly that references it.

Every usage requirement in `engine/CMakeLists.txt` is marked one of two ways:

- **PRIVATE**: the engine needs it for its own code, but users of the engine don't see it.
- **PUBLIC**: the engine needs it, *and* everything that links the engine gets it too.

| What | Visibility | Why |
|---|---|---|
| `engine/include/` | PUBLIC | It's the API that the game uses |
| `engine/src/` | PRIVATE | Engine internals |
| GLM | PUBLIC | Math types will appear in the engine's API, as `Vector3` does in Unity's |
| SDL3, Vulkan | PRIVATE | Implementation details. The sandbox can't even include their headers |
| `VIVA_DEBUG` define | PUBLIC | `VIVA_ASSERT` gets expanded inside game code, which must see the define too |
| `VIVA_VERSION_*` defines | PRIVATE | Only `Version.cpp` uses them |

**Presets** (`CMakePresets.json`) are named configurations. Each one picks the generator, the
build folder, Debug or Release, and the compiler, much like Unity's Build Profiles. CLion and the
command line read the same file, so they build the same way. Every preset builds into its own
`build/<preset>/` folder, so Debug and Release files never mix.

**Debug vs Release.** Debug turns off optimization and adds full debug info and runtime checks.
Our code adds asserts and Trace logs on top of that. Release is optimized and drops all of it.

### Static libraries

A **static library**, such as `VivaEngine.lib` or `SDL3-static.lib`, is a bundle of object files.
At link time, the linker copies the parts that are actually used into the executable. A
**dynamic library** (`.dll` or `.dylib`) is loaded at runtime instead, which is how C# assemblies
work. Static linking is why `Sandbox.exe` runs without an SDL3.dll next to it.

The one runtime library we *do* load is the **Vulkan loader**, `vulkan-1.dll`. On Windows it
normally comes with the GPU driver. The "Vulkan loader" line in the output proves the engine found
and called it.

### FetchContent: packages, CMake style

`cmake/Dependencies.cmake` declares SDL3 and GLM with a git URL and a pinned tag. On the first
configure, CMake clones them into `build/<preset>/_deps/` and builds them as part of our project.
It's the same idea as adding a Unity package from a git URL ending in `#v1.2.3`. Nothing is
installed system-wide, and every build uses exactly the same versions.

Vulkan is the exception. It comes from the LunarG SDK installed on the machine, found with
`find_package(Vulkan)`, because the SDK also brings tools we need: the validation layers (from
M2) and the `glslc` shader compiler.

**SYSTEM** marks third-party headers as "system" headers, and the compiler doesn't report warnings
from inside those. Our own targets get a high warning level (`/W4` on MSVC, `-Wall -Wextra` on
Clang). Together, these mean every warning you see points at our code.

### Compile definitions: Unity's Scripting Define Symbols

A **compile definition** is a `-D` flag passed to the compiler, such as `-DVIVA_DEBUG`. It works
exactly like a symbol in Unity's *Scripting Define Symbols*:

```cpp
#if defined(VIVA_DEBUG)
    // only compiled into Debug builds
#endif
```

`$<$<CONFIG:Debug>:VIVA_DEBUG>` is a CMake **generator expression**, meaning "add VIVA_DEBUG, but
only in the Debug configuration". The engine version reaches the code the same way:
`project(VivaEngine VERSION 0.1.0)` is the only place it's written, and CMake passes it to
`Version.cpp` as `-DVIVA_VERSION_MAJOR=0` and so on.

### Why the game never sees SDL or Vulkan

Your Unity scripts never call Direct3D or Metal; the engine wraps them. VivaEngine follows the
same rule. The sandbox, standing in for a game, only includes `Viva/...` headers, plus GLM,
which is public on purpose. PRIVATE linking enforces this: the command that compiles `Main.cpp`
doesn't contain SDL's or Vulkan's include folders at all.

Inside the engine there are two folder rules:

- SDL and anything specific to one operating system go only in `src/Platform/`.
- Vulkan goes only in `src/Renderer/`.

The build doesn't enforce these; they're conventions we keep. M0 already shows how they work:

- `Version.h` declares four functions. Each one is defined in the folder that's allowed to use
  its library: `GetSDLVersion()` in `Platform/`, and both Vulkan queries in `Renderer/`.
- `Platform/Debugger.cpp` holds the engine's first `#if defined(_WIN32)` /
  `#elif defined(__APPLE__)` blocks. The rest of the engine just calls
  `BreakIntoDebuggerOrExit()`.

When the Mac port comes, every platform-specific line to check is in one folder.

### Log: templates and std::format

`Log::Info("Loaded {} meshes in {:.2f} ms", count, ms)` is the engine's `Debug.Log`.

- **`std::format`** (C++20) plays the role of C# string interpolation. `{}` takes the next
  argument, and `{:.2f}` prints it with 2 decimals. The format string is **checked at compile
  time**, so `Log::Info("{} {}", onlyOneArgument)` doesn't build.
- **Templates.** `template <typename... Args>` lets `Info` accept any number of arguments of any
  type, like C#'s `params object[] args`. The difference is that the compiler generates a
  separate, fully typed version for each combination of argument types, so nothing is boxed.
  Template code has to sit in the header, because the compiler needs the full body at every call
  site to generate those versions. Non-template code (`Write`, `IsEnabled`) lives in `Log.cpp` as
  usual.
- **`Log() = delete;`** removes the constructor, so nobody can create a `Log` object. That's how
  C++ spells a C# `static class`.
- **Thread safety.** `Write` locks a `std::mutex` through a `std::lock_guard`. The guard locks in
  its constructor and unlocks in its destructor, at the closing brace, so it's C#'s
  `lock (obj) { ... }` and can't be forgotten. Tying a resource to an object's lifetime like this
  is called **RAII** ("Resource Acquisition Is Initialization"). It will matter a lot once we own
  Vulkan objects.
- Warnings and errors go to **stderr**, which CLion's console shows in red, and the rest goes to
  stdout. Every line is flushed immediately, so nothing gets lost if the program dies.

### VIVA_ASSERT: macros

`VIVA_ASSERT(index < count, "index {} out of range", index)` is the engine's `Debug.Assert`.
Unity strips `Debug.Assert` from non-development builds (it's marked
`[Conditional("UNITY_ASSERTIONS")]`), and `VIVA_ASSERT` does the same in Release.

It has to be a **macro**, because only the preprocessor can:

- turn the condition into text (`#condition` becomes `"index < count"`),
- capture the *caller's* file and line (`__FILE__`, `__LINE__`),
- remove the check from Release builds completely. The condition isn't even evaluated there, so
  never put code with side effects inside an assert.

Details worth noticing in `Assert.h`:

- **`__VA_OPT__(, ...)`** is a C++20 feature meaning "insert this only if extra arguments were
  passed", which is what makes the message optional. MSVC's traditional preprocessor predates the
  standard, so the engine turns on its conforming one with `/Zc:preprocessor`. That flag is
  PUBLIC, because the macro gets expanded inside game code.
- **`do { ... } while (false)`** turns the macro into one statement, so
  `if (x) VIVA_ASSERT(y); else ...` behaves as it reads.
- In Release, the macro becomes **`(void)sizeof(!(condition))`**. `sizeof` only inspects the
  expression's type and never runs it. Without it, a variable used only inside an assert would
  trigger an "unused variable" warning in Release.

When an assert fails, `AssertFailed` logs the condition, the message, and the file and line, then
calls `BreakIntoDebuggerOrExit()`. With a debugger attached, execution stops there, and the call
stack leads back to the failed assert. Without one, the program exits with code 1. It deliberately
avoids `std::abort()`, because in Windows Debug builds that shows a modal "abort() has been
called" dialog.

**No exceptions.** The brief bans exceptions in engine code, so nothing in it uses `throw` or
`try/catch`. A broken assumption is a bug, and an assert catches it. An expected failure, such as
a missing file in a later milestone, gets reported through a return value. Most game engines work
this way. The compiler's exception support stays on (the default), because the standard library
itself can throw, for example when memory runs out.

### Small C++ idioms that appeared in M0

| C++ | Meaning | Closest C# |
|---|---|---|
| `namespace Viva { ... }` | Groups names | `namespace Viva { ... }` |
| `using namespace Viva;` | Use the names without the prefix | `using Viva;` |
| `struct Version { ... };` | Same as `class`, except members are public by default | `struct` or `class` (in C++, every type is a value type unless you use a pointer or reference) |
| `std::string ToString() const;` | The method doesn't modify the object | a `readonly` struct member |
| `static_cast<uint32_t>(x)` | Explicit conversion | `(uint)x` |
| `std::string_view` | A read-only view of text owned by someone else | `ReadOnlySpan<char>` |
| `auto` | The compiler deduces the type | `var` |
| `constexpr` | A compile-time constant | `const` |
| `[[noreturn]]` | This function never returns | `[DoesNotReturn]` |
| `namespace { ... }` (no name) | Visible only inside this `.cpp` file | the `file` modifier (C# 11) |
| `static` local variable | Initialized once, on first use, then kept between calls | a lazily initialized static field |
| `std::forward<Args>(args)...` | Passes arguments on exactly as received, without extra copies | nothing similar is needed |

### Shaders: GLSL to SPIR-V at build time

Vulkan doesn't accept shader source text, only **SPIR-V**, a compact binary format that drivers
translate into GPU code. `viva_compile_shaders()` in `cmake/Shaders.cmake` runs the SDK's `glslc`
compiler on each GLSL file during the build. The output goes to
`build/<preset>/bin/shaders/<name>.spv`, next to the executable, where the engine will look for it
in M4. Unity compiles shaders when it imports them for the same reason: a typo becomes a build
error with a file and line number, not a crash at runtime. Debug builds keep debug info (`-g`) so
RenderDoc can show the GLSL source, and Release builds optimize (`-O`).

### The MSVC developer environment

On Windows, `cl.exe` isn't on the normal `PATH`. It also needs the environment variables `PATH`,
`INCLUDE` and `LIB` pointing at the compiler, the C++ standard library and the Windows SDK.
`vcvars64.bat`, which ships with Visual Studio, sets them, and CLion's Visual Studio toolchain
runs it behind the scenes. On the command line, `scripts/build.cmd` finds the newest Visual
Studio install with C++ tools, runs `vcvars64.bat`, then configures and builds a preset. So CLion
and the command line share the same presets, generator and build folders.

## Reading guide

Read in this order. The build files come first, because they explain how the code fits together.

1. **`CMakeLists.txt`** (root). Notice:
   - `project(... VERSION 0.1.0 ...)`, the only place the engine version is written;
   - the output folders `bin/` and `lib/`;
   - the three `cmake/` helpers it includes before adding the two subfolders.
2. **`CMakePresets.json`**. Notice:
   - the hidden `base` presets and how the visible ones `inherit` from them;
   - the `condition` that hides the macOS presets on Windows, and vice versa;
   - `cl` forced as the compiler on Windows, and `CMAKE_OSX_DEPLOYMENT_TARGET` on macOS.
3. **`cmake/Dependencies.cmake`**. Notice:
   - the pinned tags;
   - the SDL options set *before* `FetchContent_MakeAvailable`, which is the call that runs SDL's
     own CMake code;
   - `SYSTEM`, and `find_package(Vulkan REQUIRED COMPONENTS glslc)`.
4. **`engine/CMakeLists.txt`**. **The most important file in M0.** Every block is a
   PUBLIC/PRIVATE decision. Compare it with the table in
   [CMake, targets and presets](#cmake-targets-and-presets).
5. **`sandbox/CMakeLists.txt`**. A single `target_link_libraries` line hands the sandbox
   everything the engine marked PUBLIC.
6. **`cmake/CompilerWarnings.cmake`** and **`cmake/Shaders.cmake`**: functions in CMake. In
   `Shaders.cmake`, notice that `add_custom_command` declares an output and its input, which is how
   Ninja knows when to re-run `glslc`.
7. **`engine/include/Viva/Log.h`**, then **`engine/src/Core/Log.cpp`**. The templates sit in the
   header and everything else in the `.cpp`. Notice the `static` local variables in `Write`.
8. **`engine/include/Viva/Assert.h`**, then **`src/Core/Assert.cpp`**, then
   **`src/Platform/Debugger.h`** and **`Debugger.cpp`**. Notice the macro's two versions (Debug and
   Release), and the OS-specific `#if` blocks hidden behind one portable function.
9. **`engine/include/Viva/Version.h`**, then its three definitions: `src/Core/Version.cpp`,
   `src/Platform/SDLVersion.cpp` and `src/Renderer/VulkanVersion.cpp`. Notice:
   - one header, three `.cpp` files in three folders, all connected by the linker;
   - the difference between the header version and the loader version in `VulkanVersion.cpp`.
10. **`sandbox/src/Main.cpp`**, the "game". It uses only `Viva/` headers and GLM.
11. **`scripts/build.cmd`**. A skim is enough.

## How to test

1. **Run it.** In CLion, select the `windows-debug` profile and the **Sandbox** configuration,
   then Run. You should see the six lines from [What was built](#what-was-built), then
   *Process finished with exit code 0*.
2. **Release.** Switch to the `windows-release` profile and run again. The `[Trace]` line is gone.
3. **A failed assert.** Switch back to `windows-debug`. Edit the Sandbox run configuration and set
   *Program arguments* to `--test-assert`.
   - **Run** it. Two red `[Error]` lines show the condition and `Main.cpp:28` (the path should be
     clickable), followed by *exit code 1*.
   - **Debug** it (Shift+F9). The debugger stops inside `BreakIntoDebuggerOrExit()`. Click `main`
     in the Frames list to land on the failing assert.
   - **Release.** Run with `--test-assert` again on `windows-release`. Nothing happens, because the
     assert was compiled out.
4. **The command line.** From any terminal in the repository, run
   `scripts\build.cmd windows-debug`, then `build\windows-debug\bin\Sandbox.exe`.
5. **Optional experiments.** Revert each one afterwards.
   - Add `#include <SDL3/SDL.h>` to `Main.cpp` and build. The build fails with *cannot open
     include file*: PRIVATE linking at work.
   - Change `VERSION 0.1.0` to `0.2.0` in the root `CMakeLists.txt` and build. CMake re-runs by
     itself and the first output line changes.
   - Change `Log::Info("SDL {}", ...)` to `Log::Info("SDL {} {}", ...)` and build. The compiler
     rejects the format string. Expect a long, cryptic message, which is typical for errors
     inside templates; look for "format" in it.

## Known limitations

- No window, input or rendering yet. That starts in M1.
- No real shaders go through `viva_compile_shaders()` yet. It was tested during development with
  a temporary shader: it compiled, rebuilt only when the shader changed, and failed the build on a
  syntax error. The shader was then removed. The function assumes a single-config generator like
  Ninja, which every preset uses.
- `Log` is minimal:
  - no colors beyond CLion's red stderr;
  - no log file;
  - timestamps count from the first log line;
  - the minimum level is fixed per build type.
- stdout and stderr are separate streams, so in CLion's console a warning can occasionally appear
  one line out of order.
- A `VIVA_ASSERT` condition with a top-level comma, such as `std::is_same_v<A, B>`, needs an extra
  pair of parentheses.
- Each preset downloads and builds its own copy of SDL3, so the first configure of a preset takes
  about 30 seconds.
- macOS is untested; see [`docs/MacChecklist.md`](../MacChecklist.md).
