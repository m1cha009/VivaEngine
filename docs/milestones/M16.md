# M16: Placing and editing objects

## What was built

The editor can now **build a scene by hand**: create objects, place them, change them, delete them,
and save the result.

- **GameObject menu:** Create Empty, 3D Object > Cube / Plane / Sphere / Cylinder, and Camera.
  New objects appear 8 units in front of the editor camera (Unity puts them at its Scene view's
  pivot), get a plain white material, and are selected.
- **Edit menu:** Duplicate (Ctrl+D), Rename (F2), Delete (Del), Frame Selected (F). The keys work
  while the Hierarchy or the Scene view has the focus.
- **Hierarchy:**
  - **Right-click** an object for the Create items (as its child) and the Edit commands, or empty
    space for the Create items (as root objects).
  - **F2** renames in place: Enter or clicking elsewhere keeps the new name, Escape the old one.
  - **Drag** an object onto another to make it a child, or onto empty space to make it a root
    object. It stays where it is in the world, as in Unity.
  - A newly selected object's parents open, so it can be seen.
- **Inspector:**
  - the name, editable;
  - **mesh** and **texture** pickers: the built-in primitives, and the image files in the
    project's `Assets` folder;
  - a **Size** field for lists (MeshRenderer's parts), and **Create Material** for a part without
    one;
  - angles in degrees (a Camera's Field Of View);
  - **Add Component** (every registered type), and **Remove Component** on a component header's
    right-click menu.
- **Scene view:**
  - **click to select**: a ray from the mouse, tested against each object's bounding box;
  - the selection **outlined** in orange (the bounding boxes of what it and its children draw);
  - a **ground grid**: lines every unit, stronger every ten, the X axis red and the Z axis blue,
    fading into the distance;
  - **F** frames the selection by its real size.
- **Project window:** double-click a `.gltf`/`.glb` model to place it in the scene.
- **Duplicates** are named like Unity's: "Cube (1)", "Cube (2)".
- **Engine additions:**
  - **`Bounds`** (`Viva/MeshData.h`): every mesh records the box its vertices lie in when it's
    created (`Renderer::GetBounds`).
  - **`Scene::Instantiate(original, assets, parent)`**: a deep copy, Unity's `Instantiate`.
  - **`Scene::Destroy(Component&)`**: removes a component at the end of the frame.
  - **`Transform::SetParent(parent, keepWorldPose)`**, `CanSetParent` and `IsBelow`; the
    free function **`DecomposeMatrix`**.
  - **`Renderer::DrawGrid`**, with a new shader pair (`shaders/Grid.vert`/`.frag`), and pipeline
    settings for see-through drawing (`AlphaBlend`, `DepthWrite`, `DepthBias`).
  - **`FieldVisitor::Angle`**, `ComponentRegistry::GetNames`, `Assets::GetPrimitiveNames`,
    `GetFileExtension`.
  - `Application::GetRenderer`, `GetAssets` and `GetScene` are public, so editor code outside the
    Application can read them.

## Concepts

### One door for every edit

The Hierarchy, the Inspector, the Scene view and the menus all change the scene, but none of them
does it directly. They ask **`SceneEditor`** (`editor/src/SceneEditor.h`): `Create`, `Duplicate`,
`Delete`, `Rename`, `Reparent`, `AddComponent`, `RemoveComponent`. Each edit selects what it made
and marks the scene as changed (the `*` in the title).

Why bother, when a window could just call `scene.Destroy(object)`? Because of **M17's undo**. To undo
an edit, something has to record it, and that's only reliable if every edit passes through one
place. Unity's equivalent is `Undo.RecordObject` and `Undo.RegisterCreatedObjectUndo`, which every
editor window must remember to call. Here no window can forget, because the windows can't edit
without `SceneEditor`.

The Edit commands follow the same idea. `EditorMenus.cpp` has one table of them: label, shortcut
text, key. The Edit menu, the Hierarchy's right-click menu and the keyboard all read it, so a menu
always shows the key that really works, and all three run the same `EditorApp::RunEditCommand`. The
Create items work the same way: one table of names and meshes feeds both the menus and `Create`.
Adding a Capsule would be one line there, plus one line in `Assets.cpp`'s primitive table.

### Picking: a ray through the mouse

Unity's Scene view finds what you clicked by shooting a **ray** from the camera through the mouse
pointer (`HandleUtility.GUIPointToWorldRay`) and testing what it hits. `SceneView::RayThrough` does
the same in three steps:

1. **Mouse to "normalized device coordinates":** the image's left edge is x = -1 and its right edge
   x = 1. Its bottom is y = -1 and its top y = 1. That's flipped from screen y, which runs down.
2. **Back through the camera:** the projection matrix squeezed everything the camera sees into a box
   whose depth runs from 0 (near plane) to 1 (far plane). Its **inverse** undoes that. The point at
   depth 0 lands on the near plane, the point at depth 1 on the far plane, and the ray runs from one
   to the other. Dividing by `w` undoes the perspective divide.
3. **Test each object** (`Picking.cpp`), and keep the nearest hit.

Testing the ray against every triangle would be exact. Instead it's tested against each mesh's
**bounding box**: the smallest box, lined up with the mesh's own axes, that holds all its vertices.
The box is computed once, when the mesh is created (`ComputeBounds`). After that the vertices live
only on the GPU. Unity's `Mesh.bounds` is the same thing, stored as a center and a size.

An object can be turned, scaled and moved, so its box can sit at any angle in the world. Rather
than turning the box into the world, `IntersectBounds` moves the **ray into the object's space**,
with the inverse of its world matrix, where the box is axis-aligned again. There the **slab test**
works:
- A box is where three "slabs" overlap: min.x ≤ x ≤ max.x, and the same for y and z.
- The ray is inside each slab between two distances: where it enters and where it leaves.
- It's inside the box from the latest entry to the earliest exit. If those cross, it missed.

The direction isn't normalized after the move, so a distance along the ray means the same point in
both spaces, and the nearest object can be found by comparing distances.

`ForEachDrawnBox` walks the boxes an object draws: its MeshRenderer's parts, if it's active and not
destroyed, and optionally its children's. Picking, F (`GetWorldBounds`) and the outline all use it,
so they agree on what counts.

### Drawing over the image: the outline

The selection's outline isn't drawn by the renderer. It's drawn by **ImGui's draw list**, as 2D
lines over the Scene view's image. Each box corner is projected the way the GPU would, with the
camera's projection × view, then mapped onto the image. M17's gizmos will be drawn the same way,
which is also how ImGuizmo works.

One trap: a point **behind the camera** projects to the wrong side of the picture. An edge that
reaches behind the camera would then shoot across the screen. `SceneView::DrawLine` cuts each line
where it crosses the near plane (z = 0 in clip space) before projecting it. That's clipping, the
same job the GPU does for triangles.

### The grid: a shader that draws lines

The grid has no line meshes at all. It's **one big square** on the ground. Its vertex shader builds
the square's corners from `gl_VertexIndex` (no vertex buffer) and centers it under the camera. Its
**fragment shader** works out, for each pixel, how close it is to the nearest grid line:

- `fract(position - 0.5) - 0.5` is the distance to the nearest line, in grid cells.
- **`fwidth`** says how far one pixel reaches, in cells. The GPU shades pixels in 2×2 groups and can
  compare neighbors, which is how it knows. Dividing by it turns the distance into **pixels**, so
  lines stay about one pixel wide near and far.
- Where cells get only a few pixels wide, the lines would merge into shimmering patterns (moiré).
  They fade out before that happens, and the 10-unit lines take over.
- Everything fades with distance, so the grid has no visible edge.

Three new pipeline settings make it see-through (`PipelineSettings` in `Pipeline.h`):
- **`AlphaBlend`:** the pixel is mixed with what's behind by its alpha (Unity's
  `Blend SrcAlpha OneMinusSrcAlpha`). Between the lines, alpha is 0 and nothing changes.
- **`DepthWrite = false`:** the grid is tested against the depth buffer, so objects hide it, but it
  doesn't write depth itself (Unity's `ZWrite Off`). It's drawn after everything solid.
- **`DepthBias = -1`:** the grid's depth is pulled slightly towards the camera (Unity's
  `Offset -1, -1`). A floor exactly at y = 0 would otherwise fight the grid for each pixel
  ("z-fighting") and flicker.

Grid.frag had a `discard` at first, for the pixels between lines. Validation flagged it: glslc turns
`discard` into a Vulkan 1.3 instruction (`OpDemoteToHelperInvocation`) whose device feature the
engine doesn't enable. Alpha 0 already blends to nothing, so the `discard` went.

### Instantiate is save, then load

How do you copy a GameObject with all its components, when each component type has different
fields? **Unity's `Instantiate` serializes the original and deserializes a copy.** `Scene::Instantiate`
does exactly that with M13's scene-file code: `SaveGameObject` turns the object (and its children)
into JSON in memory, and `LoadGameObject` builds new objects from it. Nothing touches the disk. Every
registered component copies itself through its `VisitFields`, with no copy code per type.

The price is the same as a scene file's: unregistered components, and meshes or textures made in
code, can't be written, so the copy goes without them (with a warning). An editor scene never has
those.

### Removing a component later

`Scene::Destroy(GameObject&)` has only *marked* objects since M10, and removed them at the end of
the frame, because code may still be running that uses them. `Scene::Destroy(Component&)` now does
the same for a single component: it's marked, stops updating, and `RemoveDestroyed` takes it out
before drawing. Unity's `Destroy(component)` behaves the same way.

### Staying put when the parent changes

`SetParent` has kept the local values since M10, so a moved object jumps to the same spot relative
to its new parent. Dragging in a hierarchy should do the opposite: the object stays where it is, and
its local values change. That's Unity's `SetParent(parent, worldPositionStays: true)`.

The new local matrix must satisfy *parent's world × local = world*, so
**local = inverse(parent's world) × world**. A Transform stores position, rotation and scale, not a
matrix, so **`DecomposeMatrix`** takes the matrix apart:
- column 3 is the position;
- the lengths of the first three columns are the scale;
- those columns, divided by their scales, are a pure rotation.

This is the code the glTF loader already used for node matrices (M11), moved to `Transform.cpp` so
both use it. A parent that's scaled unevenly *and* rotated can make a child's matrix skew, which no
position, rotation and scale can express. The result is then the nearest fit, the same compromise
as Unity's `lossyScale`.

### Not editing what you're walking

The Hierarchy draws by walking the scene's lists, recursively. If a right-click menu created an
object *during* that walk, `m_GameObjects` could grow and move its elements under the loop. Moving a
child changes the `children` vector being looped over. So edits that add or move objects are
**deferred**: the Hierarchy stores them in a `std::function` (a stored piece of code, like a C#
`Action`) and runs it after the tree is drawn. Delete only marks objects, so it's safe at any time.

### Drag and drop in ImGui

A tree node becomes a **drag source** with `BeginDragDropSource` and carries a **payload**: here,
the GameObject's address, tagged with the type name "GameObject". Another item becomes a **target**
with `BeginDragDropTarget` and takes payloads of that type. The Hierarchy only makes a node a
target if the dragged object may go below it (`CanSetParent`: not below itself or its own
children). So an impossible drop doesn't light up at all. The empty space below the tree is an
`InvisibleButton`: an item of its own, so it can take drops, clicks and a right-click menu.

### Keys belong to a window

Del deletes the selection, but only while the **Hierarchy or the Scene view** has the focus.
Otherwise Del in, say, the Console's filter field would delete objects. Single keys are read through
`Input`, which already ignores them while any text field has the keyboard (M9). This also lets the
automated tests press them, since ImGui ignores posted keys. `EditorMenus.cpp`'s `ReadEditShortcut`
reads all four, Ctrl+D included. The File menu's Ctrl shortcuts stay ImGui shortcuts, as in M15.

### Small pieces

- **`FieldVisitor::Angle`** marks a float as an angle in radians. Its default just calls `Field`,
  so files still store radians. The Inspector overrides it to show degrees. That's the visitor
  pattern's flexibility: a new kind of field costs one virtual function, and only the visitors that
  care override it.
- **Rename rules** live in `SceneEditor::Rename`: an empty name is refused (it would be a blank,
  unclickable line), and the same name changes nothing (no `*`).
- **Tables instead of `if` chains:** `Assets.cpp` keeps the primitives in one array of
  `{ name, function }`. A *pointer to a function* (`MeshData (*Build)()`) is C++'s plain version of
  a C# `Func<MeshData>`.

## Reading guide

1. **`editor/src/SceneEditor.h`** and **`.cpp`**: every edit, in one place. Then
   **`EditorMenus.cpp`**: the two tables, and the functions that draw and read them.
2. **`editor/src/EditorApp.cpp`**: `DrawEditor` (windows, then the Edit keys and commands),
   `DrawMenuBar` (Edit and GameObject menus), `RunEditCommand`, `OpenFile`.
3. **`editor/src/SceneView.cpp`**: `Draw` (the click), `RayThrough`, `DrawLine` (near-plane
   clipping), `DrawSelectionOutline`, `Frame`, `Render` (the grid).
4. **`editor/src/Picking.cpp`**: `ForEachDrawnBox`, `IntersectBounds` (the slab test),
   `PickGameObject`, `GetWorldBounds`.
5. **`shaders/Grid.vert`** and **`Grid.frag`**, then `Renderer::Impl::Initialize` (the grid's
   pipeline settings) and `RecordGrid` in **`engine/src/Renderer/Renderer.cpp`**, and the new
   fields in **`engine/src/Renderer/Pipeline.h`** / **`.cpp`**.
6. **`editor/src/HierarchyWindow.cpp`**: `Draw` (reveal, deferred edits), `DrawNode` (drag and
   drop, the right-click menu), `DrawRenameField`, `DrawEmptySpace`.
7. **`editor/src/InspectorWindow.cpp`**: `PickAsset`, the new `Field` overrides (mesh, texture,
   material, `Angle`), `BeginList`'s Size, and the name, Add Component and Remove Component in
   `DrawInspectorWindow`.
8. **The engine:**
   - **`engine/src/Scene/SceneFile.cpp`**: `Scene::Instantiate`.
   - **`engine/src/Scene/Scene.cpp`** and **`GameObject.cpp`**: `Destroy(Component&)` and
     `RemoveDestroyedComponents`.
   - **`engine/src/Scene/Transform.cpp`**: `SetParent` with `keepWorldPose`, `CanSetParent`,
     `DecomposeMatrix`.
   - **`engine/include/Viva/MeshData.h`**: `Bounds`.
9. **`editor/src/ProjectWindow.cpp`**: texture names for the picker, and model files.

## How to test

1. **Open a project** in VivaEditor. A grid lies on the ground, with a red X axis and a blue Z axis.
2. **Create:** GameObject > 3D Object > Cube. A white cube appears in front of the camera and is
   selected: orange outline, Inspector filled, `*` in the title. Try a Sphere, a Plane and a Camera.
3. **Select by clicking** in the Scene view: click an object to select it, and the sky to deselect.
   Press **F** to frame the selection.
4. **Edit in the Inspector:**
   - Type a new name.
   - Change the Position.
   - Pick a texture (copy `assets/textures` into the project's `Assets` folder first, and press
     Refresh in the Project window).
   - Set the material's Color.
   - Add Component > Spinner. It doesn't turn: Edit mode.
   - Right-click the Spinner's header > Remove Component.
5. **Hierarchy:**
   - Ctrl+D duplicates ("Cube (1)").
   - F2 renames.
   - Del deletes.
   - Right-click an object > Create Empty makes a child, and its parent opens.
   - **Drag** a cube onto another: it becomes a child but doesn't move. Drag it onto empty space:
     it's a root object again, still in place.
6. **Models:** in the Project window, double-click `models/CesiumMilkTruck.glb` (copy
   `assets/models` into the project first). The truck appears, outlined part by part.
7. **Build a little level:**
   - Scale a Plane into a floor.
   - Duplicate a cube into a wall and a few steps.
   - Give them colors.
8. **Save, close, reopen:** Ctrl+S, close the editor, open it and the project again. The scene is
   as you left it.
9. **Keys stay in their window:** click in the Console's area and press Del. Nothing is deleted.

## Known limitations

- **No lighting:** a white cube's faces all look the same, so shapes read only by their outline
  and colors. Lighting is a "Beyond M18" item; see the note to Michail in the M16 summary.
- **Boxes, not triangles:** picking uses bounding boxes, so a click just outside a sphere (inside
  its box) picks it. Cameras and empty objects can't be clicked in the Scene view; select them in
  the Hierarchy.
- **Dragging only reparents:** objects can't be reordered among their siblings, and a duplicate goes
  to the end of its parent's list (Unity puts it right after the original).
- **One selection:** no Ctrl-click or box selection.
- **No gizmos or undo** yet (M17): move objects by typing or dragging values in the Inspector.
- **The mesh picker lists the primitives only;** models are placed whole from the Project window.
- **New objects aren't snapped** to the grid.
- **Instantiate copies what a scene file holds** (see above).
- **The grid's lines are faint on a light floor**, as Unity's are.
