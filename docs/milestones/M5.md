# M5: Buffers and GPU memory

## What was built

The engine draws meshes from data in GPU memory: a triangle, a quad and a hexagon side by side.
Their vertices and indices come from buffers, uploaded once at startup.

- **`Buffer`** (`engine/src/Renderer/Buffer.h/.cpp`): a Vulkan buffer plus its memory.
  - `MemoryLocation::Gpu` for data only the GPU uses; `MemoryLocation::CpuToGpu` for data the CPU
    writes.
  - `Buffer::CreateWithData` fills a `Gpu` buffer through a temporary **staging buffer**.
  - M5 has **two commits**. The first allocates memory **by hand** (memory types,
    `vkAllocateMemory`, `vkBindBufferMemory`). The second switches to **VMA**, the Vulkan Memory
    Allocator.
- **`VulkanContext::ImmediateSubmit`**: records a one-off command buffer, runs it and waits for
  the GPU. The staging upload uses it.
- **`Mesh`** (`engine/src/Renderer/Mesh.h/.cpp`): a vertex buffer and an index buffer, drawn with
  `vkCmdDrawIndexed`.
  - `Vertex` is position + color.
  - `kVertexBindings` and `kVertexAttributes` describe that layout to a pipeline.
  - `MeshData` is the CPU-side version: vertices plus triangle indices.
- **`PipelineSettings`** gained `VertexBindings` and `VertexAttributes`.
- **New shaders:** `shaders/VertexColor.vert` and `.frag` read the vertex buffer. They replace
  M4's `Triangle` shaders, which made up their own positions.
- **Debug builds log** the GPU's memory heaps and types at startup. After loading, they log how
  VMA packed the buffers into memory.
- **VMA 3.4.0** comes in through FetchContent. Its implementation is compiled once in
  `engine/src/Renderer/VmaImplementation.cpp`, and its internal checks report through
  `VIVA_ASSERT`.

## Concepts

### Vertex buffers and the vertex input layout

In M4 the vertex shader picked positions from a constant array. Now each vertex comes from a
**vertex buffer**: an array of `Vertex` structs in GPU memory. The shader declares what it
receives:

```glsl
layout(location = 0) in vec3 inPosition;
layout(location = 1) in vec3 inColor;
```

The pipeline has to know how to get from bytes in a buffer to those inputs. That's the **vertex
input layout**, in two parts (`Mesh.h`):

- **Bindings:** which buffers vertices come from, and the **stride**, the bytes from one vertex to
  the next. One binding here, with a stride of `sizeof(Vertex)` (24 bytes: two `vec3`s of three
  4-byte floats).
- **Attributes:** for each shader input (its `location`), which binding it reads, its **format**
  (`VK_FORMAT_R32G32B32_SFLOAT` = three 32-bit floats; formats double as "data types" here) and its
  **offset** inside the vertex (`offsetof(Vertex, Color)` = 12).

In Unity this is `VertexAttributeDescriptor` in the advanced Mesh API. The layout is baked into
the pipeline: drawing a different vertex format means a different pipeline.

### Index buffers

A quad is two triangles, so six corners, but only four distinct points. An **index buffer** lists
triangles as numbers that point into the vertex buffer: `0, 1, 2, 2, 3, 0`. Shared corners are
stored once. The hexagon needs 7 vertices instead of 18. With real models, most vertices are shared
by around six triangles, so this saves a lot of memory and vertex-shader work: the GPU caches
recently transformed vertices by index.

That's exactly Unity's `Mesh.vertices` and `Mesh.triangles`. `vkCmdDrawIndexed` walks the indices
and fetches the vertex each one names. We use 32-bit indices (`VK_INDEX_TYPE_UINT32`); 16-bit ones
halve the size for meshes under 65,536 vertices.

### GPU memory: heaps and memory types

A Vulkan GPU describes its memory as **heaps** (physical pools: VRAM, system RAM) and **memory
types** (ways to use a heap, with property flags). Debug builds print them at startup. On the
RTX 3080 Ti it looks like this (the flags are the `VK_MEMORY_PROPERTY_..._BIT` names, shortened
here):

```
Memory heap 0: 11.8 GiB, on the GPU
  memory type 1: DEVICE_LOCAL
  memory type 2: DEVICE_LOCAL
  memory type 5: DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT
Memory heap 1: 31.9 GiB
  memory type 0: (none)
  memory type 3: HOST_VISIBLE | HOST_COHERENT
  memory type 4: HOST_VISIBLE | HOST_COHERENT | HOST_CACHED
```

- **DEVICE_LOCAL**: on the GPU's own VRAM. That's the fastest memory for the GPU, and usually out of the
  CPU's reach.
- **HOST_VISIBLE**: the CPU can **map** it, which means getting a normal pointer to it and writing
  through that pointer. On a PC that's system RAM, which the GPU reads over the PCIe bus: fine for
  small or short-lived data, slow to draw big meshes from.
- **HOST_COHERENT**: CPU writes reach the GPU without an explicit **flush**.
- **HOST_CACHED**: the CPU caches it, which matters when the CPU *reads* GPU results back.
- Type 5 is **Resizable BAR**: VRAM the CPU can write directly. It's great for small per-frame
  data. M6's camera data may land there.

Apple Silicon (and integrated GPUs) has **unified memory**: one heap, which both the CPU and GPU
use. The macOS CI runner (MoltenVK) reports a single heap with three types:
- DEVICE_LOCAL;
- DEVICE_LOCAL | HOST_VISIBLE | HOST_COHERENT | HOST_CACHED: GPU memory the CPU can map;
- DEVICE_LOCAL | LAZILY_ALLOCATED: for attachments that only ever live in the GPU's on-chip tile
  memory and never reach RAM.

Check the log on a real Mac (it's in the Mac checklist).

### Staging buffers: getting data into GPU memory

The CPU can't write DEVICE_LOCAL memory, so data makes two hops (`Buffer::CreateWithData`):

1. Create a **staging buffer** in HOST_VISIBLE memory, and `memcpy` the data into it.
2. Create the real buffer in DEVICE_LOCAL memory.
3. Record `vkCmdCopyBuffer` from one to the other, run it on the GPU and wait.
4. Destroy the staging buffer.

Each buffer declares its **usage** up front: `VERTEX_BUFFER`, `INDEX_BUFFER`, `TRANSFER_SRC` (can
be copied from) or `TRANSFER_DST` (can be copied into). Drivers use that to pick memory and
layouts, and the validation layer complains if you use a buffer for something it didn't declare.

Unity does the same thing when you call `Mesh.UploadMeshData` or when a mesh is imported.
"Read/Write Enabled" keeps the CPU-side copy around; otherwise only the GPU copy remains.

### One-off command buffers and fences

Until now every command buffer was a frame's. `ImmediateSubmit` (`VulkanContext.cpp`) is the
loading-time version. It works through these steps:
1. create a command pool and buffer;
2. call your lambda to record into it;
3. submit with a **fence**;
4. wait for that fence on the CPU;
5. destroy everything.

It's simple and slow, because the CPU sits idle until the GPU is done. That's fine while loading.
A streaming engine would batch many uploads into one submit, or use a separate transfer queue.

The lambda is passed as `std::function<void(VkCommandBuffer)>`, C++'s equivalent of
`Action<CommandBuffer>`. `[&]` captures the surrounding variables (the staging buffer, the
destination) by reference, which is safe because `ImmediateSubmit` finishes before they go away.

### A barrier for buffers

The copy writes the buffer, and drawing reads it later. Writes on a GPU aren't automatically
finished and visible to later reads, as M3 showed for images. So after the copy, a
**buffer memory barrier** says that copy writes (`COPY` stage, `TRANSFER_WRITE`) must be done and
visible before any later reads. A barrier also orders work submitted *later* to the same queue,
which is how it reaches the frames drawn afterwards. Buffers have no layouts, so this barrier is
simpler than an image barrier.

The barrier's destination is "everything" (`ALL_COMMANDS`, `MEMORY_READ`), broader than drawing
needs. At load time that costs nothing, and it keeps `CreateWithData` correct for any use.

### Doing it by hand, then VMA

**First commit:** `git show e3f2681:engine/src/Renderer/Buffer.cpp`. The manual path is:
1. `vkCreateBuffer`;
2. `vkGetBufferMemoryRequirements`, which returns the size, alignment and allowed memory types;
3. `FindMemoryType` picks the first allowed type with the properties we want;
4. `vkAllocateMemory`;
5. `vkBindBufferMemory`;
6. `vkMapMemory` for CPU-visible buffers.

That works, but it does one `vkAllocateMemory` per buffer, and real engines can't:

- Drivers limit the number of allocations (`maxMemoryAllocationCount` is often 4096), and each one
  is slow, because it goes to the OS.
- Each allocation is rounded up to a large granularity (often 64 KiB). The triangle's 72-byte
  vertex buffer would waste nearly all of it.
- Picking the best memory type for each GPU (ReBAR, unified memory, integrated GPUs) is fiddly.

**VMA** solves all three. It allocates big **blocks** and places many buffers inside each one
(**suballocation**). It also picks memory types from a description of *how* memory is used
(`VMA_MEMORY_USAGE_AUTO`, plus "the CPU writes this sequentially" for staging). Debug builds log
the result:

```
GPU memory: 6 allocation(s) using 480 bytes, inside 2 block(s) totalling 64 MiB
```

Here, six buffers (3 meshes × vertex + index) share one block in VRAM. The second block is the one
the staging buffers used, in system RAM: VMA keeps one emptied block per memory type for reuse.
480 bytes rather than the 444 bytes of data, because each buffer starts at an aligned offset.

In the VMA version, `Buffer::Create` is one `vmaCreateBuffer` call, and `~Buffer` is one
`vmaDestroyBuffer`. Compare the two versions with `git diff e3f2681 HEAD --
engine/src/Renderer/Buffer.cpp`.

Two smaller VMA details:

- **Flushing.** VMA may pick memory that isn't HOST_COHERENT, so `Buffer::Write` calls
  `vmaFlushAllocation` after the `memcpy`. On coherent memory it does nothing.
- **Leak checks.** In Debug, VMA checks at shutdown that every buffer was destroyed.
  `VmaImplementation.cpp` routes VMA's checks to `VIVA_ASSERT`, so a leak logs the problem and
  stops the program.

### C++ notes

- **`std::span<const T>`**: a view of a contiguous array (pointer + length) without owning it, like
  C#'s `ReadOnlySpan<T>`. `PipelineSettings` uses spans for the vertex layout.
- **`std::as_bytes(span)`**: views any array as raw bytes (`std::byte`), which is what a buffer
  holds. `Buffer` takes bytes, so it doesn't care whether they're vertices, indices or (in M6)
  matrices.
- **`inline constexpr`** arrays in a header (`kVertexBindings`): compile-time constants that every
  file including the header shares, without duplicate-definition errors.
- **`offsetof(Vertex, Color)`**: the byte offset of a member within a struct, computed by the
  compiler.

## Reading guide

1. **`shaders/VertexColor.vert`**: the `in` variables at locations 0 and 1.
2. **`engine/src/Renderer/Mesh.h`**: `Vertex`, then `kVertexBindings` and `kVertexAttributes`
   (match them with the shader), `MeshData`, and `Mesh`. Then **`Mesh.cpp`**: two uploads, and
   `Draw()` binding the buffers and calling `vkCmdDrawIndexed`.
3. **`engine/src/Renderer/Buffer.h`** and **`Buffer.cpp`**: `MemoryLocation`, `Create`
   (VMA), `CreateWithData` (staging, copy, barrier) and `Write` (memcpy + flush).
4. **The manual version:** `git show e3f2681:engine/src/Renderer/Buffer.cpp`. It reads top to
   bottom as the numbered steps above. Its `FindMemoryType` is the heart of "memory types".
5. **`engine/src/Renderer/VulkanContext.cpp`**: `ImmediateSubmit`, `CreateAllocator`, and
   `LogMemoryHeaps` / `LogMemoryUsage`. Notice the destructor destroys the allocator before the
   device.
6. **`engine/src/Renderer/Renderer.cpp`**: the `Triangle`, `Quad` and `Hexagon` functions (vertices
   and indices), the meshes created in `Create()`, and `RecordDraws()`.
7. **`engine/src/Renderer/Pipeline.cpp`**: the vertex input state now filled from the settings.
8. **`cmake/Dependencies.cmake`** (the VMA block) and
   **`engine/src/Renderer/VmaImplementation.cpp`**: how a single-header library is compiled once.

## How to test

1. **Run** the Sandbox. A triangle (RGB), a quad (orange, yellow, blue, purple corners) and a
   hexagon (white center, rainbow corners) sit side by side on the dark background.
2. **Debug log:**
   - The memory heaps and types appear right after "Using NVIDIA…".
   - Each mesh logs "Mesh uploaded: N vertices, M triangles".
   - The "GPU memory:" line follows.
3. **Resize** the window: the shapes stretch with it (they're still in clip space; M6 fixes that).
   No validation output.
4. **RenderDoc:** capture a frame and select a `vkCmdDrawIndexed`.
   - The *Mesh Viewer* shows the vertex buffer's contents (VS Input) and the indices.
   - The *Pipeline State* tab's Vertex Input section shows the binding and both attributes.
   - The *Resource Inspector* lists the six buffers.
5. **Experiments** (rebuild after each, and revert afterwards):
   - In `Renderer.cpp`, change a color in `Quad()`: only that corner changes, blended across both
     triangles.
   - Change the quad's indices to `0, 1, 2` only: half the quad disappears.
   - In `Mesh.h`, set the stride to `sizeof(Vertex) - 4`: every vertex after the first is read
     from the wrong place, and the shapes turn to garbage. That's what a layout mismatch looks
     like.
   - In `VertexColor.vert`, add `layout(location = 2) in vec3 inNormal;` and use it: the
     validation layer reports that the shader reads location 2, which the pipeline doesn't
     provide.
   - In `Renderer::Create`, add `(void)renderer->m_Meshes.back().release();
     renderer->m_Meshes.pop_back();`, which leaks one mesh. At exit, VMA's leak check fails
     through `VIVA_ASSERT` ("Some allocations were not freed…"), and the program exits with
     code 1.

## Known limitations

- The vertices are still in clip space, so the shapes stretch with the window. M6 adds the model,
  view and projection matrices.
- Meshes are static: uploaded once, never changed. Data the CPU changes every frame needs one
  buffer per frame in flight, which M6 introduces for the camera.
- Each upload waits for the GPU, twice per mesh (vertices, then indices). That's fine for a few
  meshes; M11's models are still small. A bigger engine batches uploads or uses a transfer queue.
- On unified-memory GPUs (Apple Silicon), the staging copy is unnecessary, because the CPU could
  write the final buffer directly. VMA can detect that case; we keep one code path for now.
- The demo shapes live in the renderer. M8 moves "what to draw" into the sandbox.
