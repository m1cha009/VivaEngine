# M1: Window, input and game loop

## What was built

The engine now opens a window and runs a game loop. There's still nothing to draw (that's M3),
but every part a game needs around the drawing is in place.

- **`Viva::Application`**, the base class of a game. It owns the window and the main loop. A
  game derives from it and overrides `OnStart`, `OnUpdate(dt)`, `OnFixedUpdate(fixedDt)` and
  `OnShutdown`, like a `MonoBehaviour`.
- **`Window`**, an engine-internal wrapper around an SDL3 window, created as Vulkan-capable,
  resizable and high-DPI. It handles the window's own events (quit, resize) and passes keyboard
  and mouse events on to `Input`.
- **`Viva::Input`**: `GetKey` / `GetKeyDown` / `GetKeyUp` like Unity, the same for mouse buttons,
  plus mouse position, movement and wheel.
- **`Viva::Time`**: `DeltaTime()`, `FixedDeltaTime()` (50 Hz), `SinceStart()` and `FrameCount()`.
- **The main loop** runs fixed updates on an accumulator and sleeps while the window is
  minimized.
- **The version banner** moved from the sandbox into the engine. The SDL and Vulkan version
  functions are now engine internals, as planned in the M0 cleanup.
- **The sandbox** became `SandboxApp`:
  - it shows the frame rate in the title bar (through `Application::SetWindowTitle`);
  - it logs key presses, mouse buttons and the wheel;
  - **Esc** quits;
  - `--quit-after <seconds>` makes it end on its own, which CI and scripted tests use.

A Debug run looks like this (keys pressed: W, then Esc):

```
[   0.000] [Info ] VivaEngine 0.1.0 | SDL 3.4.18 | Vulkan headers 1.4.363 | Vulkan loader 1.4.363
[   0.170] [Info ] Window: 1280x720 points, 1280x720 pixels (display scale 1.00)
[   0.170] [Info ] Press keys and mouse buttons to see them logged. Esc quits.
[   0.171] [Trace] Window resized to 1280x720 pixels
[   1.170] [Trace] Last second: 60346 frames, 49 fixed updates
[   1.866] [Info ] Key down: W
[   1.933] [Info ] Key up:   W

```

## Concepts

### The game loop: Unity's player loop, made visible

In Unity, the player loop is hidden: you write `Update` and Unity calls it. Here the loop is
`Application::Run()` in `engine/src/Core/Application.cpp`, about 40 lines you can read. Each
iteration is one frame:

1. **`BeginInputFrame()`** clears last frame's "pressed this frame" and "released this frame"
   flags.
2. **`Window::PollEvents()`** asks the operating system what happened since the last frame: key
   presses, mouse movement, resize, the close button. Keyboard and mouse events go into `Input`.
3. If the window was closed, the loop ends. If it's minimized, the loop **sleeps** until the next
   event, using 0% CPU instead of spinning through empty frames.
4. **Time**: how long since the previous frame? That's `dt` (`Time::DeltaTime()`).
5. **Fixed updates**: zero or more calls to `OnFixedUpdate` (see below).
6. **`OnUpdate(dt)`**: the game's per-frame code.

From M3 on, a "render" step goes at the end, which is the same order Unity uses: input, then
FixedUpdate, then Update, then rendering.

### Delta time and the fixed timestep

Computers run at different speeds, and frames take different amounts of time. `dt` is how many
seconds the last frame took. Multiply movement by it (`position += speed * dt`) and things move at
the same speed at 30 FPS and at 300 FPS, exactly like `Time.deltaTime`. Time is measured with
`std::chrono::steady_clock`, a clock that only moves forward. Unlike the wall clock, it doesn't
jump when Windows adjusts the time.

Some code wants a **fixed** step instead. Physics is the classic case, because it behaves
differently with big and small steps. The loop keeps an **accumulator**:

- Each frame adds `dt` to it.
- While it holds at least one whole fixed step (0.02 s by default), the loop calls
  `OnFixedUpdate(0.02f)` and subtracts 0.02.

At 144 FPS (dt ≈ 0.007 s), most frames run no fixed update and every third frame runs one. At 30
FPS (dt ≈ 0.033 s), each frame runs one or two. Either way the average is 50 per second, the same
as Unity's FixedUpdate. The sandbox's Trace line "Last second: … frames, 50 fixed updates" shows
it. As in Unity, `Time::DeltaTime()` returns the fixed step while `OnFixedUpdate` runs.

`dt` is **capped at 0.25 s**. After a breakpoint or a long hitch, the game takes one quarter-second
step instead of jumping ahead by the whole pause. The fixed loop doesn't have to run hundreds of
steps to catch up, which would make the next frame slow too. That feedback loop is called the
"spiral of death".

### Inheritance and virtual functions

```cpp
class SandboxApp : public Application {
protected:
    void OnUpdate(float dt) override { ... }
};
```

`virtual` in the base class means a derived class may replace the function. That's the same idea
as C#, but the replacement is marked with `override` *after* the parameter list. `public
Application` means "derives from, publicly", like `: Application` in C#.

Two rules come with it:
- **A base class with virtual functions needs a virtual destructor** (`virtual ~Application()`).
  Otherwise, destroying a `SandboxApp` through an `Application` pointer would skip
  `SandboxApp`'s destructor.
- The `On…` functions and `SetWindowTitle` are **protected**: derived classes can use and
  override them, but outside code can't call them. `Run()` and `Quit()` are public.

### Ownership: unique_ptr and a type that's only declared

`Application` owns the window as `std::unique_ptr<Window> m_Window`. A `unique_ptr` is the single
owner of an object: when the `unique_ptr` goes away (or you call `reset()`), the object's
destructor runs. In C# the garbage collector frees objects whenever it likes; here destruction
happens at an exact, known moment, which matters for things like closing a window or freeing
GPU memory.

`Application.h` only says `class Window;`. That's a **declaration**: "a class with this name
exists". It's enough to hold a pointer to one, and it keeps SDL out of the game's sight. The catch:
destroying a `unique_ptr<Window>` needs `Window`'s full definition. That's why `~Application()`
is defined in `Application.cpp`, which includes `Platform/Window.h`, and not in the header.

### Construction that can fail: a factory function

Opening a window can fail (no display, no Vulkan driver). A C# constructor would throw, but the
engine doesn't use exceptions, and a C++ constructor has no return value. So `Window` is created
through a static **factory function**:

```cpp
static std::unique_ptr<Window> Create(const std::string& title, uint32_t width, uint32_t height);
```

It returns `nullptr` when SDL fails, after logging why. `Application::Run()` checks the result and
returns `EXIT_FAILURE`. The destructor `~Window()` is the cleanup half: it destroys the SDL window
and shuts SDL down. That's RAII again, as in M0's `lock_guard`: the resource lives exactly as long
as the object.

### The platform layer: events, physical keys, points and pixels

Only two places know about SDL's events, both in `Platform/`:
- `Window::HandleEvent` handles the window's own (quit, resize).
- `ProcessInputEvent` in `Platform/Input.cpp` handles keyboard and mouse.

**`SDL_Event` is a union**: one block of memory that holds *one of* many event structs, with
`event.type` saying which. `event.key` is only meaningful for keyboard events, `event.button` for
mouse buttons, and so on. For "is the window minimized?", the engine simply asks SDL, which keeps
that state as a window flag.

- **Physical keys.** `Key`'s values are **USB HID usage codes**, the numbers keyboards themselves
  send. SDL's scancodes use the same numbers, so converting is a single cast. To make sure the
  numbers in `Input.h` really match, `Input.cpp` checks them with **`static_assert`**, a condition
  the compiler checks while building; a wrong number stops the build. "Physical" means `Key::W`
  is the key in the W position of a US keyboard, even on a French AZERTY keyboard where it's
  labeled Z. That's what WASD controls need.
- **Key repeat.** Holding a key makes the OS send repeated "key down" events. `Input` ignores
  them, so `GetKeyDown` fires once per real press.
- **Points vs pixels.** On high-DPI screens (every Mac with a Retina display), a 1280×720
  window is measured in **points** but has 2560×1440 **pixels**. `SDL_WINDOW_HIGH_PIXEL_DENSITY`
  asks for the full pixel resolution, and `Window::GetPixelSize()` reports it. On this PC the
  display scale is 1.0, so both numbers match, but the renderer (M3) will always use the pixel
  size.

### Unity-style static classes, and who may change them

`Input` and `Time` are static classes (`= delete` on the constructor, as `Log` in M0), so game
code calls them like Unity's: `Input::GetKeyDown(Key::Space)`. Their state lives in the `.cpp`
files, in anonymous namespaces, with an `s_` prefix for "static storage". It's created when the
program starts and lives until it ends.

Only the engine may *change* that state, and the two classes show two ways to enforce it:
- **`Time`** has private functions plus `friend class Application;`, which lets exactly one other
  class call them. It's a targeted `InternalsVisibleTo`.
- **`Input`**'s public header contains only what games use. The functions that feed it,
  `BeginInputFrame()` and `ProcessInputEvent()`, are declared in the **private** header
  `src/Platform/InputEvents.h`, which games can't include at all.

### Small C++ idioms that appeared in M1

| C++ | Meaning | Closest C# |
|---|---|---|
| `class SandboxApp : public Application` | Inheritance | `class SandboxApp : Application` |
| `virtual void OnUpdate(float dt)` / `... override` | Overridable function / its replacement | `virtual` / `override` |
| `virtual ~Application()` | Destructor that also runs derived destructors | — (the GC handles it) |
| `Application({ .Title = "..." })` | Designated initializers: set fields by name | object initializers `new() { Title = "..." }` |
| `std::unique_ptr<Window>` + `reset()` | Single owner; destroys the object at a known moment | `IDisposable` + `Dispose()`, enforced |
| `class Window;` | Declaration only: the name exists | — |
| `std::optional<MouseButton>` | A value or nothing | `MouseButton?` |
| `ButtonState& state` | Reference: another name for the caller's object | `ref ButtonState state` |
| `for (ButtonState& key : s_Keys)` | Range-based for over references | `foreach (ref var key in span)` |
| `std::array<ButtonState, 512>` | Fixed-size array that knows its size | an array with a fixed length |
| `static_assert(condition)` | A check the compiler does while building | — (closest: analyzers) |
| `friend class Application;` | Lets one class use private members | `InternalsVisibleTo` (per assembly) |
| `union SDL_Event` | One memory block, several possible layouts | `[StructLayout(Explicit)]` with overlapping fields |

## Reading guide

1. **`engine/include/Viva/Application.h`**: the API a game sees. Notice:
   - the `virtual` functions and their default empty bodies;
   - `class Window;` with `std::unique_ptr<Window>`;
   - the deleted copy operations.
2. **`sandbox/src/Main.cpp`**: how a game uses it: a subclass, `override`, the designated
   initializer for the title, `SetWindowTitle` for the frame rate, and `main()` creating the app
   and calling `Run()`.
3. **`engine/src/Core/Application.cpp`**: `Run()` is the game loop. Read it top to bottom against
   [the list above](#the-game-loop-unitys-player-loop-made-visible). Notice the minimized branch,
   the `dt` cap and the fixed-step `while`.
4. **`engine/src/Platform/Window.h`** and **`Window.cpp`**:
   - `Create()`, the factory;
   - the destructor;
   - `HandleEvent()`: quit and resize here, the rest to Input;
   - `IsMinimized()`, which asks SDL;
   - `WaitForEvent()`, which leaves the event queued.
   
   Notice that `Window.h` only *declares* `SDL_Window` and `SDL_Event`, so files including it
   don't see SDL.
5. **`engine/include/Viva/Input.h`**, then **`engine/src/Platform/InputEvents.h`**: Input's public
   half (for games) and its private half (for the engine).
6. **`engine/src/Platform/Input.cpp`**:
   - the `static_assert`s;
   - `ButtonState` and `Record()`, which sets "pressed" only on a real transition;
   - `ProcessInputEvent()`, the `switch` over the union.
7. **`engine/include/Viva/Time.h`** and **`engine/src/Core/Time.cpp`**: the `friend` declaration,
   `SetDeltaTime` (used around fixed updates), and the assert in `SetFixedDeltaTime`.
8. **`engine/src/Platform/SDLVersion.h`** and **`engine/src/Renderer/VulkanVersion.h`**: the
   version queries, now private, and the banner at the top of `Run()`.
9. **`.github/workflows/macos.yml`**: the Sandbox now runs with `--quit-after 2` in CI.

## How to test

1. **Run** the Sandbox (`windows-debug`). A black, empty window opens, and after a second its
   title reads *VivaEngine Sandbox | … FPS | … ms*. The FPS number is huge (tens or hundreds of
   thousands), because nothing is drawn yet and nothing waits for the monitor.
2. **Keys and mouse.** Press keys and click: *Key down: W*, *Key up: W*, *Mouse Left down at
   (x, y)*, *Mouse wheel: +1.0*.
   - Hold a key: only one *Key down*, because repeats are ignored.
   - Try Shift, Ctrl and the arrow keys.
3. **Fixed updates.** Watch the Trace line each second: the frame count varies wildly, and the
   fixed updates stay around 50.
4. **Minimize** the window and watch Task Manager: Sandbox's CPU drops to 0%. Restore it, and the
   app continues; the minimized time doesn't count toward *Shutting down after … s*.
5. **Resize** by dragging a border: *Window resized to …x… pixels*.
6. **Quit** with Esc or the close button: *Shutting down after … frames*, exit code 0.
7. **Release** (`windows-release`): the same, without the Trace lines.
8. **Experiments** (revert afterwards):
   - In `SandboxApp::OnStart`, add `Time::SetFixedDeltaTime(0.1f);`. The Trace line drops to
     10 fixed updates per second.
   - `Time::SetFixedDeltaTime(0.0f);` trips the assert instead of hanging the game.
   - Put a breakpoint in `OnUpdate`, wait five seconds and continue. That frame counted as
     0.25 s, not 5 s.

## Known limitations

- Nothing is rendered yet, so the loop spins as fast as it can on one CPU core. Vsync arrives with
  the swapchain in M3 and fixes that.
- One window only; SDL starts and stops with it.
- **Input**:
  - no gamepads and no text input (typing into a text field);
  - the mouse position is in points;
  - `Key` names the common keys only, but every key code is still tracked.
- **Time** has no time scale (Unity's `timeScale`) yet.

## Verified on

- **Windows 11 Pro**, Debug and Release, zero warnings (warnings are errors). An automated script
  drove the real window, before and after the `/simplify` cleanup pass:
  - **Title:** the FPS appeared in it.
  - **Input:** keys W and Space were logged, as were mouse clicks and the wheel.
  - **Minimize:** **0 ms** of CPU over 2 s while minimized. Restoring and resizing were logged.
  - **Quit:** Esc and the close button both gave exit code 0 with nothing on stderr.
  - **Release:** `--quit-after` ended the app on its own with exit code 0.
- **CI (macOS):** runs both builds with `--quit-after 2`. New Mac checks are in
