# M9: Debug UI

## What was built

The engine gets an in-game debug UI, made with **Dear ImGui**, the library most engines and
graphics tools use for this. The sandbox uses it for two windows over the scene:

- **Stats** (top left):
  - FPS and a graph of the last 120 frame times;
  - fixed updates per second;
  - the renderer's numbers: draw calls, triangles, the UI's own draw calls, and GPU memory as VMA
    sees it;
  - a **VSync** checkbox, and a button for ImGui's **demo window**.
- **Camera** (top right): position, yaw, pitch, field of view and fly speed, all editable while
  the game runs, plus **Reset**.
- **F1** hides and shows both. The FPS left the title bar for the Stats window.

In the engine:

- **Dear ImGui 1.92.9b** is fetched like the other dependencies. Games get its core (`#include
  <imgui.h>`); the two "backends" that connect it to SDL and Vulkan are private to the engine.
- **`Platform/Window`** owns ImGui's context and its SDL3 backend:
  - it passes every event to ImGui;
  - it keeps the presses ImGui wants (a click on a slider, typing into a field) away from the
    game's `Input`;
  - it scales the UI to the monitor's DPI setting.
- **`Renderer/ImGuiRenderer`** wraps ImGui's Vulkan backend. The UI is drawn in the same rendering
  as the scene, after it, with a custom fragment shader (`shaders/ImGui.frag`) that gets ImGui's
  colors right on our sRGB swapchain.
- **`Viva/Renderer.h`** gains `GetStats()` (a `RenderStats` struct) and `SetVSync()`/`IsVSync()`.
- **`Application`** starts ImGui's frame before the game's updates and finishes it before
  `EndFrame`, so games build their windows in `OnUpdate`.
- **`Viva/ImGuiConfig.h`** configures ImGui at compile time. Its asserts go through the engine's
  assert handling.

## Concepts

### Immediate-mode UI

Unity has two UI systems, and Dear ImGui works like the old one. In UGUI (Canvas, Button
components) the UI is a tree of objects that exist between frames: you create a Button once and
subscribe to its `onClick`. That's a **retained-mode** UI. Unity's IMGUI, the `OnGUI` and
`EditorGUILayout` code that custom inspectors are made of, is an **immediate-mode** UI: there are
no button objects. Code describes the whole UI again every frame, and a button is a function call
that returns `true` on the frame it's clicked:

```csharp
// Unity, OnGUI
if (GUILayout.Button("Reset")) ResetCamera();
speed = GUILayout.HorizontalSlider(speed, 0.5f, 50f);
```

```cpp
// Dear ImGui, in OnUpdate (sandbox/src/DebugWindows.cpp)
if (ImGui::Button("Reset"))
    camera = *m_StartCamera;
ImGui::SliderFloat("Fly speed", &flyCamera.MoveSpeed, 0.5f, 50.0f);
```

The slider takes a pointer to the game's own variable and writes the new value straight into it.
There's no copy of the state to keep in sync, which is what makes immediate mode so quick for
debug tools: one line per widget, next to the variable it shows. The price is that the UI is
rebuilt every frame (cheap for a few windows), and that widgets are identified by their labels.
Two widgets with the same label in one window would be the same widget, so a label can carry a
hidden ID after `##`: `PlotLines("##FrameTimes", ...)` shows no text but stays unique.

`ImGui::Begin("Stats")` and `ImGui::End()` bracket a window, and every call in between adds to it.
ImGui remembers only small things between frames, such as where each window is and which widget
the mouse is dragging.

### From widgets to triangles

A frame of ImGui goes like this:

1. **`ImGui::NewFrame()`** starts the frame, with the input that arrived since the last one.
2. **Widget calls** (`Begin`, `Text`, `SliderFloat`, `End`) handle that input and append
   triangles to a list per window: text is a quad per letter cut out of a font texture, and a
   checkbox is a few rectangles.
3. **`ImGui::Render()`** finishes the lists into `ImDrawData`: vertices, indices, and draw
   commands, each a range of indices with a clip rectangle and a texture.

ImGui itself never touches the GPU or the OS. Two **backends** connect it to the rest:

- The **platform backend** (`imgui_impl_sdl3`) feeds it the window's size and pixel density,
  mouse and keyboard events, and sets the cursor shape and clipboard.
- The **renderer backend** (`imgui_impl_vulkan`) owns a pipeline, a font texture and vertex
  buffers. Each frame it uploads the vertices and records one `vkCmdDrawIndexed` per draw
  command, each with its clip rectangle as the scissor. A whole window of widgets usually comes
  to one or two draws: the Stats window reports about 4 for the whole UI.

In VivaEngine, each backend lives with the code it needs. SDL stays in `Platform/` and Vulkan in
`Renderer/`, as before:

| Piece | Owner | Created | Destroyed |
|---|---|---|---|
| ImGui context (all of ImGui's state) and the SDL3 backend | `Window` | in `Window::Create` | in `~Window`, before `SDL_Quit` |
| Vulkan backend | `ImGuiRenderer`, owned by the renderer | after the swapchain | by `~Renderer`, after the GPU is idle |

The renderer is destroyed before the window, so the Vulkan backend shuts down while the context
it belongs to still exists. Each frame, in `Application::Run`:

```
Renderer::BeginFrame()      wait for the GPU, acquire an image (+ ImGui's Vulkan NewFrame)
Window::PollEvents()        every event goes to ImGui, then to Input unless ImGui wants it
Window::NewImGuiFrame()     ImGui's SDL3 NewFrame: window size, mouse, cursor
ImGui::NewFrame()
OnFixedUpdate / OnUpdate    the game submits draws and builds its windows
ImGui::Render()             the windows become ImDrawData
Renderer::EndFrame()        scene draws, then ImGuiRenderer::Record, in the same rendering
```

### Who gets the input: the UI or the game?

A click on the Stats window's VSync checkbox mustn't also reach the game. Imagine a shooter
whose gun fires on that same click. ImGui reports what it wants in two flags, updated at every
`NewFrame`:

- `io.WantCaptureMouse` is true while the pointer is over one of its windows, or while a drag
  that started on one is still going.
- `io.WantCaptureKeyboard` is true while one of its text fields is active, for example after a
  Ctrl+click on a slider to type a value.

`Window::HandleEvent` gives every event to ImGui, then holds back from `Input` the **presses** that
ImGui wants. **Releases always pass.** `Input` already ignores the release of a key it never saw go
down, and a key the game did see go down always gets its release, so nothing can get stuck.

Unity leaves this to every game: you check `EventSystem.current.IsPointerOverGameObject()` before
reacting to a click. Here the engine does it once for all input.

Mouse look adds a twist. While the right button is held, the cursor is locked: hidden and frozen
(`Input::SetCursorLocked`, M6). The pointer ImGui would see is invisible to the player. So
`Window::NewImGuiFrame` sets `ImGuiConfigFlags_NoMouse` while the cursor is locked, and the UI
ignores the mouse until the button is released.

### Colors: sRGB, and blending in linear space

Since M3 the swapchain images are **sRGB**: shaders write linear colors, and the GPU encodes them
to sRGB on the way to memory. (That's what Unity's *Linear* color space does too.) ImGui's colors,
though, are already sRGB values, the way you'd pick them in a paint program. Written unchanged,
they'd be encoded a second time. ImGui's dark grey window background (sRGB 15/255) would come out
around 68/255, a washed-out light grey.

ImGui's Vulkan backend lets an engine replace its shaders, so `shaders/ImGui.frag` decodes the
vertex color from sRGB to linear before writing it. The GPU's encoding then gives back exactly the
color ImGui asked for: the screenshot measured 17/255 for the window background, which is ImGui's
grey with a hint of the sky behind it. The texture isn't decoded. The font atlas is white, with
the letters' shapes in alpha, and an sRGB texture shown with `ImGui::Image` is already decoded by
its sampler.

**Blending** also happens in linear space when the target is sRGB, and that one can't be undone
in a shader. ImGui's window background is 94% opaque. Blended in sRGB values, as ImGui's colors
were designed, the scene barely shows through. Blended in linear values, a bright floor shows
through clearly. So `ImGuiRenderer::Create` makes window and popup backgrounds fully opaque. The
remaining differences are small: anti-aliased text looks a little bolder, and translucent widgets
like buttons a little brighter, than in ImGui's screenshots. (The way to match ImGui exactly is to
draw it into a non-sRGB view of the swapchain image. That needs a swapchain extension and a second
rendering pass, which isn't worth it for a debug UI yet.)

All of this assumes an sRGB swapchain, like the rest of the renderer: the Unlit shader writes linear
colors too, and the textures are sRGB. A GPU that offered no 8-bit sRGB format would get colors
wrong everywhere, so `Swapchain.cpp` logs a warning when it has to fall back to another format.

### Points, pixels and DPI

Two different things are called "scale":

- **Pixel density** (macOS Retina): the window is measured in points, and each point is 2×2 pixels.
  ImGui works in points and gets the ratio from the SDL3 backend (`io.DisplayFramebufferScale`).
  The Vulkan backend then draws at full resolution, and ImGui renders its fonts at that density, so
  text stays sharp.
- **Content scale** (Windows display scaling, 125% or 150%): the window is measured in pixels, and
  the user asked for everything to be bigger. `Window::Create` reads
  `SDL_GetDisplayContentScale` and scales ImGui's style and fonts by it.

On a Mac the content scale is 1, and on Windows the pixel density is 1. So each platform gets
exactly one of the two, and the UI comes out the same physical size on both.

### Configuring a library at compile time

Some C++ libraries are configured with defines rather than settings, because the choices change
how their code compiles. ImGui reads a config header, its "imconfig". `IMGUI_USER_CONFIG`
(`cmake/Dependencies.cmake`) points it at `Viva/ImGuiConfig.h`, which every file that includes
`imgui.h` then sees first:

- **`IM_ASSERT`**: ImGui checks the rules of its API (every `Begin` needs its `End`, IDs must be
  unique). By default a broken rule calls the C library's `assert()`, whose Debug-build dialog
  would freeze the window. It's routed to `Viva::Detail::AssertFailed`, the function `VIVA_ASSERT`
  calls, which logs the check with ImGui's file and line (from `std::source_location`) and stops
  the program. The header declares that function again rather than including `Viva/Assert.h`,
  which would pull `<format>` into every file that includes `imgui.h`. As with `assert()`, the
  checks exist only in Debug builds.
- **`IMGUI_DISABLE_OBSOLETE_FUNCTIONS`** hides names ImGui only keeps for old code, so you only see
  the current API.

These defines are `PUBLIC` on the `imgui` target, because a define that differs between files
would make them disagree about what ImGui's types and inline functions are.

ImGui's own files are built as CMake **OBJECT libraries**. They're compiled with ImGui's settings
(not our warnings-as-errors), and the compiled objects go straight into `VivaEngine.lib`, as if
they were the engine's own files. A plain static library of their own would also work. But
`AssertFailed` lives in the engine, and the engine needs ImGui, so two libraries would depend on
each other.

### Render stats and VSync

`Renderer::GetStats()` returns numbers about the **last** frame drawn. The Stats window is built
during the update, before this frame is drawn, so it always shows the previous frame's numbers.

- **Draw calls and triangles:** the scene has 10 draws (floor, 8 pillars, crate) and 110
  triangles. The UI adds its own handful.
- **GPU memory** comes from VMA (M5) with `vmaGetHeapBudgets`, which is cheap enough to call every
  frame. "12 allocations, 4.11 MB in 4 memory blocks, 99.8 MB" shows VMA's sub-allocation at
  work: a dozen buffers and images share a few large `VkDeviceMemory` blocks. Those blocks are
  reserved ahead, which is why they total more than the allocations.

`SetVSync()` switches the present mode (M3) at runtime. It marks the swapchain as outdated, and
the next `BeginFrame` rebuilds it as FIFO (vsync) or MAILBOX. Uncheck VSync and the FPS jumps from
the monitor's refresh rate to thousands, as the GPU draws frames the display never shows.

## Reading guide

1. **`sandbox/src/DebugWindows.cpp`**: the game's side, and the best introduction to immediate
   mode. Look at `Begin`/`End`, widgets that take pointers to the game's variables, the `##` label,
   and `PlotLines` reading a ring buffer.
2. **`sandbox/src/Main.cpp`**: `OnUpdate` calls `m_DebugWindows.Draw`, and the title-bar FPS is
   gone.
3. **`engine/src/Core/Application.cpp`**: where ImGui's frame starts (`NewImGuiFrame`, `NewFrame`)
   and ends (`Render`).
4. **`engine/src/Platform/Window.cpp`**: `IsForImGui` (the input policy), the context and backend in
   `Create`, the DPI scaling, `NewImGuiFrame`'s cursor-lock rule, and `HandleEvent`.
5. **`engine/src/Renderer/ImGuiRenderer.h/.cpp`**: the Vulkan backend's `InitInfo` (dynamic
   rendering formats, frames in flight, our shader, failure handling), the opaque windows, and
   `Record`.
6. **`shaders/ImGui.frag`**: the sRGB decoding. Compare it with the shader text in
   `build/<preset>/_deps/imgui-src/backends/imgui_impl_vulkan.cpp`.
7. **`engine/src/Renderer/Renderer.cpp`**: `m_ImGui` in `Initialize`, `NewFrame` in `BeginFrame`,
   `Record` in `EndFrame`, the stats in `RecordDraws` and `UpdateMemoryStats`, and `SetVSync`.
8. **`engine/include/Viva/Renderer.h`**: `RenderStats`, `GetStats`, `SetVSync`.
9. **`engine/include/Viva/ImGuiConfig.h`**: `IM_ASSERT` routed to the engine's `AssertFailed`.
10. **`cmake/Dependencies.cmake`**: the ImGui section (OBJECT libraries, why `SYSTEM` is applied
    separately, the config defines).

## How to test

1. **Run** the Sandbox. Stats is at the top left, Camera at the top right. FPS matches your
   refresh rate, and fixed updates read 50 per second.
2. **F1** hides and shows both windows.
3. **Keyboard:** fly with WASD while the mouse is over a debug window. Hovering doesn't capture the
   keyboard.
4. **Mouse:**
   - Hold the right button over the scene and look around. The hidden cursor doesn't highlight the
     windows it passes "under".
   - Start the same drag over a debug window: the camera doesn't turn, because that press belongs
     to the UI.
5. **Sliders:** drag Position, Yaw, Pitch, Field of view (a zoom) and Fly speed. **Ctrl+click** a
   slider to type a value. While the field is active, WASD don't move the camera, and Esc cancels
   the edit instead of quitting. **Reset** puts the camera back where it started.
6. **VSync:** uncheck it. The FPS jumps to thousands, and the log shows a swapchain rebuilt with
   `VK_PRESENT_MODE_MAILBOX_KHR`. Check it again for FIFO.
7. **ImGui demo window:** every widget ImGui has, each with the code that makes it (in
   `imgui_demo.cpp`). Its *Tools → Metrics/Debugger* shows the draw lists and commands behind the
   UI. Close it with its X.
8. **Resize, minimize, restore:** the windows stay put and validation stays silent.
9. **RenderDoc:** after the scene's three groups of draws comes ImGui's pipeline bind, its descriptor
   sets, and a few `vkCmdDrawIndexed`, each after a `vkCmdSetScissor`.
10. **Experiments** (revert afterwards):
    - In `ImGuiRenderer::Create`, delete the `.CustomShaderFragCreateInfo = { ... }` entry. ImGui's
      own shader runs, and the UI turns washed out.
    - Delete the two lines that make the window backgrounds opaque. The floor shows through the
      windows.
    - Add an extra `ImGui::End();` at the end of `DebugWindows::Draw`. The Debug build logs
      `Assertion failed: (g.CurrentWindowStack.Size > 1) && "Calling End() too many times!"`,
      with ImGui's file and line, and stops.
    - Make a window of your own in `OnUpdate`: `ImGui::Begin("Hello"); ImGui::Text("Frame %d",
      static_cast<int>(Viva::Time::FrameCount())); ImGui::End();`.

## Known limitations

- **The UI scale is set once,** at startup, for the monitor the window opens on. Dragging the window
  to a monitor with different scaling doesn't rescale it.
- **Window positions aren't saved.** ImGui would write `imgui.ini` into whatever folder the game
  was started from, so that's switched off, and the windows reopen at their default places.
- **Blending in linear space:** see above. Text and translucent widgets look slightly different
  from ImGui's own screenshots, and so would a deliberately see-through window
  (`ImGui::SetNextWindowBgAlpha`, typical for a HUD). The full fix is to draw the UI through a
  non-sRGB view of the swapchain image in a second rendering pass, or to render the scene into an
  image of its own and copy it into a non-sRGB swapchain (the shape post-processing needs anyway).
- **Font uploads wait for the GPU:** ImGui uploads its font texture with `vkQueueWaitIdle`. That
  happens at startup and when text needs a size it hasn't drawn yet, not every frame.
- **GPU memory** counts VMA's allocations only: not ImGui's buffers and textures, and not the
  swapchain images.
- **No keyboard or gamepad navigation** of the UI. ImGui supports both, but they're off.
