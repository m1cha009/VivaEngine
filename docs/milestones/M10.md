# M10: Scene, GameObjects and components

## What was built

The game world is now made of **GameObjects with components**, the way it is in Unity. The
sandbox no longer draws anything by hand. It builds a scene, and the engine updates and draws it.

- **`Viva/Scene.h`**: the `Scene` owns every GameObject.
  - `CreateGameObject(name, parent)` makes one; `Destroy(gameObject)` removes it (and everything
    below it) at the end of the frame's updates.
  - `GetMainCamera()` finds the first active camera.
  - `Application` owns one scene; get it with `GetScene()`.
- **`Viva/GameObject.h`**: a name, a `Transform`, and components.
  - `AddComponent<T>(args...)` and `GetComponent<T>()`.
  - `SetActive` / `IsActiveInHierarchy`.
- **`Viva/Component.h`**: the base class for behavior, like `MonoBehaviour`, with `OnStart`,
  `OnUpdate(dt)` and `OnFixedUpdate(fixedDt)`.
- **`Viva/Transform.h`**:
  - local position, rotation (a quaternion) and scale, as plain fields;
  - a parent/child hierarchy;
  - the world matrix, position and directions (`Forward`, `Right`, `Up`).
- **`Viva/MeshRenderer.h`**: a mesh and a material. The scene draws every active one each frame.
- **`Viva/Camera.h`**: the camera is now a component. It looks along its GameObject's Forward.
- **Forward is +Z**, as you chose: where a model faces and where a camera looks, as in Unity.
- **Renderer:** `SetCamera(view, projection)` and `GetAspectRatio()`; `EndFrame()` takes no camera
  any more. `Application::GetCamera()` is gone.
- **Sandbox:**
  - `FlyCamera` is a component on the Camera GameObject, and a new `Spinner` component turns
    things.
  - `LoadDemoScene` builds a small hierarchy:
    - a ring of pillars that are children of one slowly turning object;
    - a crate with a small crate orbiting it, as its child.
  - The M9 Camera window became a **Scene window**: a hierarchy you can open and click, and an
    inspector for the selected object (Transform, the components it knows, an Active checkbox and
    a Destroy button).

## Concepts

### GameObjects and components

Unity's model, which M10 copies:

| Unity | VivaEngine |
|---|---|
| `new GameObject("Crate")` | `scene.CreateGameObject("Crate")` |
| `gameObject.AddComponent<Spinner>()` | `gameObject.AddComponent<Spinner>(axis, speed)` |
| `GetComponent<Camera>()` | `GetComponent<Camera>()` (a pointer, `nullptr` if absent) |
| `class Spinner : MonoBehaviour { void Update() }` | `class Spinner : public Viva::Component { void OnUpdate(float dt) override; }` |
| `transform.parent`, `transform.localPosition` | `GetTransform().GetParent()`, `GetTransform().LocalPosition` |
| `Destroy(gameObject)` | `scene.Destroy(gameObject)` |
| `gameObject.SetActive(false)` | `gameObject.SetActive(false)` |
| `Camera.main` | `scene.GetMainCamera()` |

A GameObject on its own is just a named place in the world, its Transform. Everything else comes
from components: a `MeshRenderer` makes it visible, a `Camera` makes it a viewpoint, and the game's
own components (`FlyCamera`, `Spinner`) make it do things. Behavior is composed from small pieces
instead of inherited from one big class. That's why it scales to large games, and why Unity
was built that way.

Unlike Unity, `AddComponent` passes its arguments to the component's constructor
(`AddComponent<MeshRenderer>(mesh, material)`), so a component can be complete from the start.

### Who owns what

```
Application
└── Scene                          std::unique_ptr: destroyed before the renderer
    └── GameObject (each)          std::unique_ptr in the scene's list
        ├── Transform              a member: lives and dies with its GameObject
        └── Components             std::unique_ptr in the GameObject's list
            └── MeshRenderer ──→ Mesh, Material (std::shared_ptr, M8: freed when the last user goes)
```

Everything has exactly one owner, so destroying the scene (at shutdown) or a GameObject (with
`Destroy`) cleans up all of it automatically. That's RAII again, from M2.

Everything else is a plain, non-owning pointer:
- a Transform's parent and children;
- a component's GameObject;
- whatever a game remembers, such as the inspector's selected object.

C# doesn't have this distinction, because its garbage collector keeps anything alive that's still
referenced. In C++, a pointer to a destroyed object "dangles": it points at memory that's been
freed, and using it is undefined behavior (usually a crash, sometimes something worse). Unity
softens this with its "fake null": a destroyed `UnityEngine.Object` compares equal to `null`. Here
the rule is simple: **after `Destroy`, forget the object**. The debug UI shows one way to do that:
before using its selected object, it checks the object is still in the scene.

The scene keeps GameObjects through `unique_ptr`, so they never move in memory. The `std::vector`
of pointers may move to a bigger block as it grows, but the objects themselves stay put, so
pointers and references to them stay valid.

### The life of a component

1. **`AddComponent<T>`** constructs it and attaches it to its GameObject. The constructor runs
   before the component is attached, so set-up that needs `GetGameObject()` or `GetTransform()`
   belongs in `OnStart` (the same rule as Unity's constructors and `Start`).
2. **`OnStart`** runs once, at the start of the next update, before the component's first
   `OnUpdate` or `OnFixedUpdate`. Components on inactive objects wait until the object is active.
3. **`OnFixedUpdate` and `OnUpdate`** run while the object is active (and not destroyed).
4. **`Destroy`** only marks the object and everything below it. They're removed at the end of the
   frame's updates, before drawing. Code still running this frame may be using them, which is
   why Unity defers it too. Removing one destroys its components: their **destructors** are the
   place for clean-up, like `OnDestroy`. They run once the objects have left the scene's list, so a
   destructor may create or destroy other objects. At shutdown, `Run` destroys the whole scene
   after `OnShutdown`, while the game and the renderer still exist.

The order within a frame, in `Application::Run`:

```
Renderer::BeginFrame, input, ImGui NewFrame
for each fixed step:  Scene::FixedUpdate (OnStart for new components, OnFixedUpdate), game's OnFixedUpdate
Scene::Update         OnStart for new components, then OnUpdate for all
game's OnUpdate       after the components, like Unity's LateUpdate: debug windows, quitting
Scene::Render         remove destroyed objects, SetCamera from the main camera, Submit every MeshRenderer
ImGui::Render, Renderer::EndFrame
```

The update loops count with an index rather than iterating. A component's `OnUpdate` may create
GameObjects or add components, and adding to a `std::vector` can move its contents. A range-based
`for` loop would then read memory that's no longer the vector's.

### Transforms and the hierarchy

A Transform holds three local values: `LocalPosition`, `LocalRotation` and `LocalScale`. They're
relative to the parent, or to the world for a root object. `LocalMatrix()` combines them as
translate × rotate × scale (applied right to left: scale, then turn, then move, as in M6).

The world matrix is the parent's world matrix times the local one:

```
World(child) = World(parent) × Local(child)
```

That multiplication is the whole trick of a scene graph. A point on the small crate goes from the
small crate's space into the big crate's space, and from there into the world. Every ancestor adds
its own move, turn and scale. So the pillars, children of the turning "Pillar ring", orbit
without any code of their own. The small crate, placed 1.5 units from its parent, ends up 1.8
units from the center (1.5 × the big crate's 1.2 scale), and inherits its tumbling.

`WorldMatrix()` recomputes the chain on every call. For a few hundred objects a couple of levels
deep, that's nothing. Unity instead caches each world matrix and marks children "dirty" when a
parent moves; that's worth doing once scenes get big.

The world matrix's columns are the object's own axes as the world sees them, which is how
`Forward()`, `Up()` and `Right()` come out:

- **`Forward()` is +Z** (your choice, to match Unity): the way a model faces, which is also how
  glTF models are made, and the way a camera looks. A truck's `Forward()` is its front, and a camera
  that should look where the truck goes takes the truck's rotation.
- **`Up()` is +Y.**
- **`Right()` is -X.** In a right-handed world, facing +Z with +Y up, your right hand points to -X.
  Unity's world is left-handed, so there it's +X. It only shows when you read raw coordinates.
  Code that uses `Right()` reads the same as in Unity.

`SetParent` keeps the local values, so an object moves along with its new parent. That's Unity's
`SetParent(parent, false)`. Unity's default instead keeps the world position, which takes more
math that nothing needs yet.

### Quaternions

Unity stores rotations as `Quaternion`s, and so does the Transform (`glm::quat`). Three angles
(Euler angles) are easier to read, but:
- **Gimbal lock:** with some angle combinations, two of the three axes line up and one way of
  turning is lost.
- **They combine badly:** turning by A and then by B isn't simply adding their angles.

A quaternion is four numbers that encode "turn by this angle around this axis", and it has
neither problem:
- **Make one:** `glm::angleAxis(angle, axis)`.
- **Combine:** multiply them, like matrices, read right to left. `FlyCamera` builds its rotation
  as `angleAxis(yaw, Y) * angleAxis(-pitch, X)`: tilt first, then turn.
- **Where the order matters:** `Spinner` puts its step in front, `step * rotation`, so each frame's
  step turns around the parent's axis. `rotation * step` would turn around the object's own,
  already turned, axis instead.

The inspector shows rotations as Euler angles, converting both ways every frame. That can jump
near 90° around X, where two different angle sets mean the same rotation. Unity's inspector avoids
this by remembering the angles you typed.

### Templates: `AddComponent<T>(args...)`

`AddComponent` is a **template**: the compiler writes a separate version for each component type
it's used with. That's why it's defined in the header, where every file that calls it can see the
code. (C# generics are compiled once; C++ templates are stamped out per type.) Three features
work together in it:

- `typename... Args` is a **parameter pack**: any number of arguments, of any types.
- `std::forward<Args>(args)...` passes them on to `T`'s constructor exactly as they came in.
  Temporaries stay movable, so a `shared_ptr` argument is moved rather than copied.
- `static_assert(std::is_base_of_v<Component, T>, ...)` checks at compile time that `T` really is
  a component. `AddComponent<int>()` stops the build with a readable message, instead of a wall of
  template errors.

### `GetComponent` and `dynamic_cast`

`GetComponent<T>()` walks the object's components and asks each whether it is a `T`, with
`dynamic_cast<T*>`. That's C#'s `as` operator: it returns the pointer if the object really is a
`T` (or derived from one), and `nullptr` otherwise. It works because `Component` has virtual
functions: such objects carry runtime type information. It's a linear search, just like Unity's,
so code that needs a component every frame should look it up once and keep the pointer.

### The camera is a component

The camera became a component with a field of view and clipping planes. Wherever its GameObject is
and however it's turned, the camera is there, looking along its `Forward()`. So moving the camera
is moving a GameObject, which is what `FlyCamera` does through the Transform.

Its view matrix comes from `glm::lookAt(position, position + forward, up)`, fed with the camera's
own position and directions. lookAt turns the world so the camera looks down -Z: the direction the
OpenGL-style projection expects (M6). And because the directions are normalized, a scaled parent
can't stretch the view; Unity's camera ignores scale too.

Each frame, `Scene::Render` asks the renderer for the aspect ratio, builds the main camera's
projection, and hands both matrices to `Renderer::SetCamera`. The renderer stays unaware of
scenes, GameObjects and components: it still only receives matrices and draws.

### How an ECS differs

The other common design is an **Entity Component System**: Unity's DOTS, Bevy, or the EnTT
library. It splits things differently:

- An **entity** is just an ID, a number, with no data or code of its own.
- A **component** is plain data with no functions, like `Position { x, y, z }`. All components of
  one type sit together in one tightly packed array.
- A **system** is a function that runs over every entity that has a given set of components, for
  example "for every entity with Position and Velocity: position += velocity × dt".

Because a system reads arrays in order, the CPU's caches work at their best, and systems are easy
to run on several threads. That makes ECS the choice for tens of thousands of objects. The cost is
a less direct way of thinking: there's no "this crate" object with its own methods.

GameObjects with virtual `OnUpdate` are the opposite trade-off. They're easy to reason about, and
they're how you already think in Unity. They're slower per object, because every object is a
separate allocation and every update a virtual call. At the scale of this engine's games that
doesn't matter, which is why you chose them.

2. **`sandbox/src/Spinner.h/.cpp`** and **`sandbox/src/FlyCamera.h/.cpp`**: two components, in the

3. **`engine/include/Viva/Component.h`**, **`GameObject.h`**, **`Transform.h`**, **`Scene.h`**,
   **`MeshRenderer.h`**, **`Camera.h`**: the public API. In `GameObject.h`, read the two

   **`engine/src/Renderer/Renderer.cpp`**: `SetCamera`, `GetAspectRatio`, and `EndFrame` using the
   stored matrices.
8. **`sandbox/src/DebugWindows.cpp`**: `DrawSceneWindow`, `DrawHierarchyNode` (a recursive ImGui
   tree) and `DrawInspector` (`GetComponent` in action).

## How to test

1. **Run** the Sandbox. The scene looks as in M9, but now the pillar ring turns slowly and a small
   crate orbits the big one. The Stats window shows 11 draw calls and 122 triangles. The Scene
   window, top right, lists 13 GameObjects.
2. **Hierarchy:** open "Pillar ring" (its arrow) and "Crate". Click an object to select it.
3. **Inspector:**
   - Select "Camera": its Rotation reads (12, -180, 0), meaning tilted 12° down and turned around
     to face the middle (-180 and 180 degrees are the same turn). The three angles are taken apart in Unity's order: around Z, then X,
     then Y.
   - Drag the crate's Position or Scale: the small crate follows, and its size changes with its
     parent's scale.
   - Select a pillar and drag its Position: it keeps riding the ring, now at a new spot.
   - Change a Spinner's Speed, or the Camera's Field of view.
4. **Active:** untick it on "Crate". The crate and its child disappear, the draw calls drop to 9,
   and the hierarchy grays them out. Tick it again.
5. **Destroy:** select "Crate" and press Destroy. Both crates go, and the selection is cleared.
   GPU memory drops from 12 allocations to 9: the crate texture and the cube mesh's two buffers
   had no other users, so the renderer freed them (M8's deferred deletion). Destroy "Pillar ring"
   too: 2 objects and 7 allocations remain.
6. **Fly** as before. The camera is now a GameObject with a `FlyCamera` component.
7. **Experiments** (rebuild after each, and revert afterwards):
   - In `LoadDemoScene`, make the camera a child of the crate:
     `scene.CreateGameObject("Camera", &crate)`. You're carried along, tumbling. `FlyCamera`
     assumes a root object, so flying gets odd.
   - Write a component of your own, like a `Bobber` that moves its object up and down with
     `std::sin(Time::SinceStart())`, and add it to the small crate.
   - In `Spinner::OnUpdate`, swap the multiplication to `transform.LocalRotation * step`, and watch
     the crate's tumbling change.
   - Destroy an object from a component (`GetGameObject().GetScene().Destroy(GetGameObject())`
     after a few seconds), the way a bullet or a pickup removes itself.

## Known limitations

- **Pointers dangle after `Destroy`.** There's no Unity-style "fake null". A game must forget the
  objects it destroys (or check they're still in the scene).
- **World matrices are recomputed** on every call, recursively. That's fine for hundreds of
  objects; thousands would want caching.
- **`GetComponent` and the scene's draw loop are linear searches** with `dynamic_cast`. That's fine
  at this scale.
- **One MeshRenderer is drawn per GameObject** (the first). Several meshes need several
  GameObjects.
- **Components can't be removed or disabled** on their own, only their whole GameObject.
- **No `LateUpdate`, `OnEnable`/`OnDisable`, or messages between objects.** The game's `OnUpdate`
  runs after the components, which covers the most common `LateUpdate` use.
- **`SetParent` keeps local values.** There's no "keep the world position" option yet.
- **One scene.** There's no scene loading or switching, and no saving to a file.
